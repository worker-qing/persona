# Prompts

Every prompt personad writes for a model lives in `server/internal/prompts/`: one file per prompt, using Go `text/template` syntax, embedded in the binary with `//go:embed`.
Callers only prepare data (machine lists, how to address the owner, collected context, and so on) and call this package's typed render functions to get text. Go code no longer builds prompts with `fmt` / `+`.
`prompts` does not depend on `hub`, `kb`, or `node`. Data structures are defined in `prompts`; callers convert their own types.

What counts as a prompt: system / user text sent to a model, CLAUDE.md written to the assistant directory, snapshots at the start of each message, the first message sent into a chat,
and explanatory text that wraps data in a prompt (`<persona-context>` blocks, lines such as "类型：飞书私聊"—"Type: Lark direct message"). The user's own words, collected chat history, and document bodies are **data**, not template content.
MCP tool descriptions and parameter explanations shown to models are also prompts, in `mcp/` (see "MCP tools" below). Tool-result text returned to models still lives in the respective code.

## Template rules

- Template names are paths without `.md` (`inbox/triage`); one prompt references another with `{{template "shared/user_rules" .}}`.
  Compose an Agent's sections (body, optional sections, lists) with `{{if}}` / `{{range}}` / `{{template}}` inside the template, not string concatenation in Go.
- **The file's final newline does not count** (editors always add one). Leave a final blank line if the prompt itself must end in a newline. `TestFilesEndWithANewline` requires every file to end with a newline.
- Defaults belong in templates (`{{or .Owner "用户"}}`—"user", the default sentence when no requirements are given), not callers. Different prompts use different default forms of address ("用户" / "我" / "你"—"user" / "I" / "you"); preserve them exactly.
- Template functions (`prompts.go`): `attr` (XML attribute escaping), `ctx` (body inside `<persona-context>` / `<persona-context>` blocks; see next rule), `output` (Agent answer in a voice `<agent_output>` data block: removes opening and closing tags for that block, `AgentOutput`), `join`, `indent`, `blank` (whitespace only), `first` (first n slice elements).
  Data preparation such as truncation (`textfmt.Clip`, `textfmt.OneLine`) belongs in the caller; passed values are already ready to insert.
- **Always pass other people's text inside blocks through `ctx`** (#3754). Quotes, forwarded messages, Inbox bodies, knowledge summaries, snapshot sections, and memory indexes may come from others (or paraphrase their words). A closing tag in the body can end the block early, turning subsequent text into the user's own words. `ctx` (`ContextBody`) removes closing tags once, then replaces `<` in the resulting text with `&lt;`; matching is case-insensitive and allows whitespace on either side of the slash and before `>` (readers recognize only literal `</persona-context>` / `</persona-context>`; this is a superset).
- A template is parsed the first time it is rendered, together with the templates it includes (`missingkey=error`), so a process holds only the prompts it writes (#2475). A syntax error panics at that render;
  `Names()` parses every template, so the tests surface it first, and `TestEachTemplateParsesItsIncludes` checks that rendering any template on a fresh set parses everything it may include.
  Rendering errors (wrong field names) panic directly, never handing a partial prompt to a model. `TestEveryTemplateIsUsed` catches unused templates.
- To write literal `{{` in a prompt: `{{"{{"}}`.
- Where user-facing output instructions say "use Chinese", replace that with a `Language` field (the language's own name, `English`, `日本語`; callers use `assistant.answerLanguage(hello.Locale)`, passing empty for zh-Hans),
  and `{{if .Language}}用{{.Language}}{{else}}用中文{{end}}` in the template ("use [Language]", otherwise "use Chinese"). Empty remains byte-for-byte identical to the original, leaving existing goldens unchanged; en / ja have separate `*.en.golden` / `*.ja.golden`
  (`assistant/claude_md.md`, `inbox/triage.md`, `inbox/group.md`, `inbox/draft.md`, `tools/session_title.md`; `docs/protocol/i18n.md`).
  Knowledge-base prompts (`kb/`) remain Chinese; see `docs/protocol/i18n.md`, "Follow-up work".
- Voice prompts (all under `voice/` since #3501; `instructions.md`, `target.md`, `agent_message.md`, `status.md`, `folded.md` in #3502, `ask.md`, `needs_you.md`, `answered.md` in #3504, `progress.md`, `observed.md`, `failure.md` in #3503, `nudge.md` in #2297) have three whole-language versions. `Lang` is an i18n code (`en`, `ja`, otherwise Chinese),
  with `{{if eq .Lang "en"}}…{{else if eq .Lang "ja"}}…{{else}}…{{end}}` in the template. Goldens are `voice/testdata/prompts/<name>.<branch>.<zh-Hans|en|ja>.golden`
  (`go test ./internal/voice -run Golden`, `UPDATE_GOLDEN=1` to update). The fast layer speaks to the user; writing in the user's language makes the model continue in that language.

## Change a prompt

1. Edit the file under `server/internal/prompts/`.
2. Run golden tests and check that the differences are intended: `cd server && go test ./internal/hub ./internal/assistant ./internal/kb ./internal/node ./internal/voice -run Golden`.
3. After confirming, update goldens: `UPDATE_GOLDEN=1 go test ./internal/hub ./internal/assistant ./internal/kb ./internal/node ./internal/voice -run Golden`, and commit the `testdata/prompts/*.golden` diffs too.
   `TestGoldenAssistantContextMain` requires Postgres (runs only in `scripts/test/test-server.sh`). To update it, run on the hub machine with `UPDATE_GOLDEN=1`
   (`GOCMD='env UPDATE_GOLDEN=1 go test -count=1 -run TestGoldenAssistantContextMain' ./scripts/test/test-server.sh ./internal/hub`), then copy the two files back.
4. A judge's prompt (task done, delegation, triage): run its live check before and after the edit and put both tables in the PR ("Behaviour checks" below).

Note that `scheduleHeader` in `assistant/schedule.go` recognizes copied-back old headers by the first few lines of `assistant/task_run.md`: changing those lines requires updating it too.

## Add a prompt

1. Add `xxx.md` in the appropriate scenario subdirectory (or create a subdirectory if none fits, and add it to `//go:embed` in `prompts.go`).
2. Add a data structure and `RenderXxx` to that scenario's Go file; callers only fill the data.
3. Add a golden test in the caller's package (follow existing `*_golden_test.go` patterns: representative inputs, optional sections present / absent, empty / multi-item lists), and generate with `UPDATE_GOLDEN=1`.
   Use placeholder inputs only (`Example user`, `example.com`); `scripts/privacy_check.py` checks them.

## Behaviour checks

Goldens pin the text a prompt renders to, not what a model decides on it. The judges that make one model call also have written-out cases with what the hub should end with, and a check that asks a real model about them (#2586):

| Judge | Prompts | The model call and the hub's rules after it | Purpose | Cases | Tests |
| --- | --- | --- | --- | --- | --- |
| Task done | `assistant/task_done.md`, `task_done_input.md` | `judgeTaskDoneWith` (`assistant/done.go`) | `inbox.judge` | `assistant/testdata/judge/task_done.json`: the verdicts that pass, plus the delivery state where it matters | `TestTaskDoneScenariosAreWellFormed`, `TestTaskDoneJudgeLive` |
| Delegation | `agents/delegate.md`, `delegate_input.md` | `judgeDelegateWith` (`assistant/delegate.go`) | `agent.delegate` | `assistant/testdata/judge/delegate.json`: answer or ask, the options that pass when it answers, and options the hub refuses on its own (red-line words) | `TestDelegateScenariosAreWellFormed`, `TestDelegateJudgeLive` |
| Triage | `agents/triage.md`, `triage_input.md` | `judgeTriageWith` (`assistant/agents_triage.go`) | `agent.triage` | `assistant/testdata/judge/triage.json`: done, unsure or blocked on the user / an agent / something external, plus the request, link or agent the card must carry | `TestTriageScenariosAreWellFormed`, `TestTriageJudgeLive` |

- Every case is synthetic and public: no real conversation, person, project or message.
- `Test…ScenariosAreWellFormed` runs with the other tests and needs no model. It checks that the cases are consistent with the hub: the values are ones the hub gives, and a model answering as a case expects leaves the hub with that result after its own rules (for example a done task held at a PR is undelivered, a red-line option is left to the user, a question the reply does not contain is dropped).
- `Test…JudgeLive` asks a real model and prints one row per case (expected × got). It runs only with `PERSONA_LIVE_AI='{"base_url":"…","api_key_file":"…","model":"…"}' go test -run 'TaskDoneJudgeLive|DelegateJudgeLive|TriageJudgeLive' -v ./internal/assistant`, never in CI. A case the model gets wrong fails.
- A case the hub is known to get wrong today carries `known` (why): the live check prints it as `KNOWN` and does not fail on it, so a run fails only on a regression. When a fix lands and the case passes, drop `known` in the same PR.

When you change one of these prompts, the hub's rules after the model, or the model behind the purpose, run that judge's live check before and after, and put both tables in the PR. A real case a judge got wrong goes in as a new synthetic case, rewritten so it names no real person, project or message.
