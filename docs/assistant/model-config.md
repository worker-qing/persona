# Model providers and model configuration

## What the three entry points control

- **Settings › Model Providers**: connection method, API protocol, gateway, encrypted credentials, default model, and existing launchers on your computers. The old “Models” page lives here; existing synchronization, hiding, details, and quota features remain.
- **Settings › Model Settings**: configures five default-model categories: main chat, Agents, information processing, information screening, and question delegation. Each selects a provider, specific model, and supported thinking effort. Their purposes follow them, with two opt-in exceptions: the Inbox's **AI twin** and **Lark /agent** can each override Agents and can be reset to follow it. Named [model profiles](model-profiles.md) switch the category bindings and launcher model fields together; `agent_start` and `task_plan` can select a profile tier or explicit model override. The assistant's default launcher / model is selected only under “Main Chat” here; a chat switched to another model in the chat keeps that until it is reset (“A conversation's own model”).
- **Settings › Assistant**: Persona itself: proactive work (scheduled tasks, run history), understanding you (about me, memory), Skills, the machine it runs on, and its working directory. It neither displays nor configures models (#1291): the “Assistant” row on the settings home page has no launcher name, and the page has no “Chat model” entry. This is consistent across iOS, Mac, web, and Android. Switching one chat's model from the chat itself is not configuration either: the pick stays with that chat (“A conversation's own model”).

The home page has five category rows and separate **AI twin runs** and **Lark /agent** rows, each showing whether it is separately configured or follows Agents. “Applies To” remains read-only and collapsed by default; those two rows open their own editors rather than the Agents category. The manager supplies the catalog and descriptions (forwarded by hub; see “Who owns models” below). Model names take priority; provider details live in the editor. “Unverified” is not repeated across the home page, but real errors and rate limits still appear.

| Category | Preserved configuration ID | Scope |
| --- | --- | --- |
| Main chat | `assistant` | Direct chats with the current persona, scheduled tasks |
| Agents | `agent.new` | New Agents, AI twin execution and Lark `/agent`, each unless separately configured |
| Information processing | `kb` | Translation, reply drafting, knowledge organization and session compaction, project organization and action-item extraction, chat titles and Agent label names, answers in an attended meeting (`meeting.answer`), drafting source subscription recipes (`subscription.recipe`, called by the manager through `models.purpose_complete`, `docs/extensions/subscriptions.md` "Drafting with a model") |
| Information screening | `inbox.triage` | Inbox triage and summaries, importance assessment, deciding whether a reply or Agent handoff is needed, automatic Agent session-name corrections and periodic refreshes (#4812, `docs/assistant/agent-work.md` "Automatic session names (#4812)") |
| Question delegation | `agent.delegate` | First assesses whether to answer an Agent's question on the user's behalf (#3029, `docs/assistant/assistant.md`, “Assistant answers questions first”). Added as the fifth category on 2026-11-05: this assessment must be more accurate than triage and must not follow information screening's cheap model. If never selected, it uses information screening's connection with the model changed to Opus 5.5 (`claude-opus-5-5`; if that connection is not for Claude models, it keeps its own model). Change the provider or model here. “Inherited From” shows the actual connection name and model (`inheritedLabel`; before 2026-11-06 it always said “Model uses Opus 5.5,” which was wrong for non-Claude connections or a manually changed model). Explicitly selecting a connection hides the inheritance source |

The background supervisor (`docs/assistant/unified-entry.md` "Background supervisor") runs under the purpose `assistant.supervise`: it follows Main chat until it is given its own launcher, model or effort with `PATCH /api/v1/model-config/purposes/assistant.supervise` (sparse, revision-checked, a record of its own under `model_config.assistant.supervise`), so it can run on a cheaper or a stronger model than the main chat. The purpose is read and set through its own ID only: the catalog `GET /api/v1/model-config` returns does not list it. The clients ask for it by its ID to list it: the web, which lists it right after Main chat with what it is for (#5082, `docs/web/web.md` "Background supervisor"); the Apple apps, which ask for it by its ID beside the catalog (#5083, `docs/apple/ios.md` "Background supervisor"), and Android, which asks for it by its ID after the catalog and lists it in Model configuration and in Settings › Assistant (#5084, `docs/android/android.md` "The background supervisor (#5084)"). It applies when the background supervisor's conversation starts and on every message sent to it.

“Triage and summary” currently runs as one call, entirely under information screening; categories do not split it into two calls. persona gets no separate model override. A voice plugin's upstream audio model stays within that plugin's scope, outside the four launcher / text-API categories; text tasks handed from voice to the main chat use the main-chat model. This does not take over external Claude Code Skills or users' existing external sessions.

## Providers and execution methods

| Execution method | Used for | Constraints |
| --- | --- | --- |
| Direct API | Triage, assessment, translation, drafting, knowledge processing, titles | Messages, Responses, or Chat Completions; the manager reads / decrypts credentials and sends requests itself |
| Launcher | Claude Code / Codex chats and Agents | Must exist on the execution machine; the CLI/app-server must actually receive the specific model |
| Plugin model | Integrated voice services | Only models provided by that plugin can be selected; the plugin's own provider and credentials are not changed |

The original `/launchers` API remains. New connections have `kind` of `launcher` or `api`; omitted on legacy entries, it still means launcher. Messages-protocol API connections (`api` empty or `messages`) can also be selected for the main chat and Agents: node starts claude with their address and key (#2455; see `docs/integrations/claude-integration.md` for environment variables). Responses and Chat Completions connections support only direct calls; `finishModel` refuses to treat them as launchers. Chat Completions can be configured manually, while extension provider declarations accept only Messages and Responses. Legacy API connections (`ai`, `inbox.*_ai`, `kb.ai`, in the manager's `manager.json` since 2026-11-06, in `hub.json` before) appear as compatibility sources; authentication-file paths and values are not returned to clients.

## Execution form

`ModelPurpose.launch` is a read-only value derived from the purpose's `kind` and ID or parent, not from its provider.
It is returned by the model-configuration list and detail endpoints, never stored in a binding, and rejected in PUT/PATCH.

| Purpose | `kind` | `launch` | Execution |
| --- | --- | --- | --- |
| `assistant`, `schedule`, `task.*`, `assistant.supervise`, `inbox.agent`, `lark.agent` | `launcher` | `headless` | Background process, without a terminal panel |
| `agent.new` | `launcher` | `engine` | Interactive Agent in the target computer's terminal host |
| `kb`, `inbox.triage`, `agent.delegate`, other API purposes, `extension.*` | `api` | omitted | HTTP requests sent directly by the assistant |
| `plugin.*` | `plugin` | omitted | The plugin's own model service |

Non-launcher purposes always have an empty launch value, even if their parent is a launcher.
`applyModel` overwrites any caller-supplied `launch` in node-call params. `startOn` requires `headless` before
`assistant.send`; a new `AgentStartParams` requires `engine` before `session.start`. Existing launcher, model, effort,
runtime, permission and resume choices are unchanged.

The web page groups purposes by `(kind, launch)`: **Persona chats · Background process**, **Agents · Interactive**,
**Background processing · Direct API**, then **Extensions** (only when installed; extensions' own API purposes stay here).
These groups describe execution, not inheritance levels. The AI twin and Lark /agent sit alongside the main chat in the
background-process group, each with **Inherits the Agents model · Runs as a background process** when following Agents, or
**Separately configured** when overridden. Their reset action still says **Follow Agents**. Only **New agent** sits in the interactive group.
Scheduled tasks follow the main chat's category; this presentation does not add independent task settings.

Each row's neutral execution chip has a fixed form and a backend that follows the effective provider and runtime:
`Background process · claude -p`, `Background process · codex app-server`, `Background process · Agent SDK`,
`Interactive · herdr · claude`, or `Direct API · Messages` / `Responses` / `Chat`.
The terminal host is a computer setting, not a provider property: only a purpose bound to a known computer shows its
configured default host; `agent.new` says **By machine**. The editor previews backend changes before saving.

The trailing **?** expands an inline explanation on desktop hover, keyboard focus or click (including touch).
Click pins or closes it; Escape or a click outside dismisses it. This stays inside the settings card so long explanations
remain readable on narrow screens and at larger text sizes, without nesting a help button inside the edit button.
The explanation covers environment, configuration directories, compatible providers, typical uses and the current backend:
headless processes use the assistant's working directory and the launcher's environment/configuration;
interactive Agents use the target computer's terminal host environment and launcher configuration;
direct API purposes use provider connections/credentials and no terminal or Claude/Codex profile;
plugins use their own environment, configuration and credentials.
**Unverified** means launcher execution on the target computer has not been confirmed, not that a paid model request succeeded or failed.

## Sending through a computer (#4775)

API purposes are HTTP requests the manager sends from its own machine. When that machine has no route to the provider
(a locked-down server, a home server behind a restrictive network) while one of the user's computers does, an API
connection can name that computer under **Send through** (`via_machine`). Empty is **The hub itself**, the behavior
before this setting.

- **What moves**: only the network hop. The manager still builds every request (prompt, model, parameters, headers)
  and reads every answer (stream parsing, errors, the upstream gate); the request goes to that computer's node as one
  `model.http` call (`docs/protocol/protocol.md`, "hub ↔ node RPC"), and the node sends it with its own network and
  proxy settings. "Test connection" and "Fetch models" go the same way, so a test says what real calls will do.
- **Credentials**: the manager decrypts the key as before and puts it in that one call's headers. The node never stores,
  logs or shows it, never puts it in an error, and zeroes the params once read. No key is configured on the computer.
- **Streaming**: the node reads the streamed answer to its end (at most 16 MB) and returns it whole; the manager parses
  it as it would a direct stream. Calls that only use the final text behave the same.
- **Cancelling**: when the manager stops waiting (a timeout, a stopped conversation) it sends `rpc.cancel` and the node
  ends the request; the call's deadline goes along as `timeout_ms` (capped at 10 minutes on the node).
- **Redirects**: the node never follows one; it returns it, and the manager's client decides as it would without the node.
- **Offline or gone**: an offline computer fails the purpose at once with "<computer> is offline", without falling back
  to the manager's network and without retries; a computer this manager no longer has says so; an older node without
  the `model_http` capability says to update it.
- **Which computers**: only a direct API connection (`kind: "api"`), and only a computer this manager carries (another
  manager's machines are not its to call). Others are 400. Changing it clears the connection's recorded failures.

## Editing and inheritance

Each category shows both “In Effect” and “Model Settings”:

- Empty provider: inherit; empty specific model: use that source's default model.
- Changing providers clears the previous model and thinking effort, preventing fields from different providers being combined.
- “Restore defaults” clears only that category's choices; it takes effect after “Save,” and all its purposes reset together.
- The web provider wizard can test all three direct API protocols and discover paginated model lists. Catalog context windows take precedence over server-reported values; a server value fills a missing catalog window. If discovery fails, a valid model ID can be entered. Saving is not a paid-availability test. Chat Completions uses Bearer authentication and supports direct model purposes; reasoning effort is available for Responses and Messages, not Chat Completions. Voice uses its own real-time provider configuration, independently of these model connections.
- Offline, protocol mismatch, missing provider, and similar states are explicit. An invalid explicit configuration never silently switches providers. Direct-API providers with custom headers, proxy, or no_proxy are rejected because the manager cannot honor those settings. Existing stored entries remain available for repair: explicitly clear these fields in the provider settings; saving, named connection testing/discovery, and direct calls otherwise refuse the unsupported configuration.
- Concurrent edits to the same item from two devices use revision checks. Conflicts retain the draft and require reloading before saving again.

For launcher purposes without a bound machine (such as Agents), saving a specific model uses the model picker's online-machine selection among the provider's reported machines. This also applies to effort-only edits with an existing model and to model-profile switches. If every candidate is offline, the binding can still be saved without a live model check; it remains unverified. A purpose bound to a known machine still validates there, and an online node's model-validation error still rejects the save. These checks do not make a paid model request.

For API purposes (triage, assessment, drafting, translation, knowledge processing, titles), when there is no override or legacy `ai` configuration in the manager's `manager.json`, automatically choose a connection directly callable from the hub: first the first `kind: api` entry, then the first Persona-managed launcher with a key and Messages protocol (excluding hidden entries or those missing an address / default model / key). Use its default model. “Inherited From” shows “Automatic selection”; no override is written, and later selections here still take priority. Automatic selection by these built-in categories alone does not block provider deletion when another eligible connection can take over: the next eligible connection takes over, while an explicit provider choice (or deleting the last provider that leaves no eligible connection) still returns 409. If none exists, status and errors explain where to configure one (#388, 2026-11-02: with only “Claude Code default” configured, reply drafting immediately returned no model configured). Both Responses and Messages protocols support thinking effort configuration; Information screening (`inbox.triage`) defaults to no thinking (`effort: "off"`), including after a provider-only selection, while explicit effort levels are preserved. The caller maps `off` to Responses `none` and the model's supported Messages no-thinking mode (`thinking: {"type":"disabled"}`, or `between_tools` for Sonnet 5.5); Messages models that cannot disable thinking use `output_config.effort: "low"` instead.

Launchers such as “Claude Code default” are only CLIs on computers, without an API address or key, so they cannot be called directly and are not offered for API purposes.

## Lark /agent override (#5921)

`lark.agent` is an editable launcher purpose with `parent: "agent.new"` and `category_id: "agent.new"`, not a sixth default category. It supports the same provider (including launcher providers), model, and effort fields as Agents, but not the main-chat runtime. Nonempty fields override the Agents binding; choosing a different provider drops the inherited model and effort before applying this purpose's selections. With an empty binding, the next new `/agent` conversation inherits Agents, including subsequent changes to Agents. Saving does not change existing conversations or permissions.

GET `/api/v1/model-config/purposes/lark.agent` returns this purpose's own revision, override, effective binding, and writable fields. PUT and the compatibility PATCH endpoint share sparse updates and optimistic locking. To restore following Agents, send the current revision and explicit `null` for `provider`, `model`, and `effort`; omitting fields leaves them unchanged. Stale revisions return 409 without overwriting a draft.

**Dormant settings do not revive:** new user saves use `model_config.overrides.v1.lark.agent`. The retired `model_config.lark.agent` record, its revision, and old extension launcher defaults are neither copied nor consulted. Before the first new save, the independent revision is 0 and the override is empty, even when the old record exists. Reset stores an empty binding at the next revision in the new namespace; it never falls back to the retired record. Category-default/provider assignment does not populate the opt-in record, and provider deletion protects a provider used only by this override.

The web catalog includes the separate row and a reset-to-follow action. Android uses its existing `/agent` model entry and editor. The Apple editor edits a child with writable `fields` in place and redirects a read-only one to its category (#5925, #6029).

## AI twin override (#4232)

`inbox.agent`, the model the Inbox's AI twin starts its handling chats on (`docs/assistant/inbox.md`, "AI twin: handling chats and suggestions"), is set apart exactly like Lark /agent: an editable launcher purpose with `parent` and `category_id` `agent.new`, the same fields, validation (Agents' launchers only, no effort on Codex) and API, its own revision, and **Follow Agents** to reset. The twin is a high-volume, short-lived background job, so people run it on a cheaper or faster model than the Agents they start themselves; before this, that meant changing every new Agent too.

- **Unset follows Agents**: with nothing saved, or after a reset, the next handling chat starts on Agents' binding, including later changes there. Nobody who doesn't open this row sees a change.
- **Its own namespace**: a save goes only to `model_config.overrides.v1.inbox.agent`. The retired `model_config.inbox.agent` record, its revision and the old `inbox.agent.launcher` are neither read nor copied; before the first save the revision is 0 and the override empty.
- **Its machine**: launcher and model checks run on the computer the twin starts on (`inbox.agent.machine` when the hub has it, else the assistant's). That choice, the twin's switch and its rules are Inbox settings and are not part of this purpose.
- **Unchanged elsewhere**: saving changes neither Agents nor Lark /agent, and running handling chats keep the launcher they started on. Provider deletion is refused while only this override uses the provider; category-default assignment never writes it; model profiles switch categories only.

Clients find these rows by data, not by ID: a purpose with `parent: "agent.new"` and writable `fields` is an Agents override (web `agentsOverride`, Android `agentsOverride`, Apple `ModelConfigurationModel.followsAgents`), shown with "Separately configured" / "Follow Agents". An older hub that still sends `inbox.agent` with `fields: []` keeps it a read-only use of Agents.

## Extensions' own purposes (#6102)

An extension granted the `models` scope (docs/extensions/extensions.md "Model calls") gets an API purpose `extension.<extension id>`, named after the extension, in the group "Extensions":
`kind: "api"`, `parent: "kb"`, `category_id: "kb"`, with its own record (`model_config.extension.<id>`), revision and writable `provider` / `model` (`effort` with a Responses or Messages connection), the same shape as Lark /agent.
With an empty binding it follows "Information processing" (`kb`), including later changes there; a pick here is the extension's alone and does not touch `kb`. Its `model.complete` calls resolve this purpose at the start of each call,
so a change applies from the next call. The extension never chooses the connection and never sees a key. The prefix is not `plugin.`: the apps take `plugin.<id>` for a voice plugin and fetch its own model list for it. No budget, no cap and no fallback model (the user's decision).

`GET /api/v1/model-config` lists these purposes after Lark /agent; the manager tells the assistant which extensions have one (`app.call plugins.models`: enabled, compatible, granted `models` itself; the legacy `hub_api` full access does not count).
A switched-off or uninstalled extension's purpose is gone (404) and its record stays dormant until the extension is back. Each call's usage goes back to the extension in the result and into one log line of the manager; nothing is metered or limited. Chat Completions calls ask the server to stream that usage (`stream_options.include_usage`); a server that rejects the field gets the request once more without it and its usage reads zero.

Deleting a Persona-managed provider used by a current extension purpose returns 409, naming the extension in the same localized "still used" error as categories and Lark /agent. The provider and the extension's binding remain unchanged. Switch the extension to another provider in Model configuration, or clear its binding to follow "Information processing" before deleting; deletion is still refused if that inherited configuration or another current purpose uses the provider. Dormant records for extensions absent from the current catalog do not block deletion.

## Legacy configuration compatibility and unified application (#697)

No configuration copying or bulk database changes: reuse the four existing records `model_config.assistant`, `model_config.agent.new`, `model_config.kb`, and `model_config.inbox.triage` as category settings, preserving revisions and atomic concurrency checks. Without explicit selections, main chat uses the assistant's original default; Agents uses the original new-Agent default (Claude Code); information processing uses the old `kb.ai` / compatible triage-API baseline; information screening uses the old triage-API baseline. If the API baseline has no connection, continue automatically selecting a connection callable from the hub.

Other `model_config.*` purpose records, old `inbox.agent` / `lark.agent` dedicated launchers, assessment-specific APIs, and scheduled tasks' `Launcher/Model/Effort` no longer create hidden overrides. Original records remain for traceability. Resolution reads the owning category, except a newly saved opt-in AI twin or Lark /agent binding or a task's own binding, all in their separate namespaces. Do not claim every legacy purpose is preserved exactly.

Creating or normally editing a task through the tasks API or the app does not accept model settings, and returned task views do not show the legacy `Launcher` / `Model` / `Effort` fields; a task's own model configuration goes through its model purpose instead. Scheduled tasks (purposes `schedule`, `task.<task id>`) follow “Main chat” (#1570, old tracker #1544, decided 2026-11-04; they belonged to Agents before #697): they run in the assistant's working directory with its instructions, memory, and tools, so they are assistant chats, not newly created Agents. Under Agents, an unconfigured task used default Claude Code, making the “Morning briefing” fail every time with `Not logged in` on a hub machine not logged into it. New task runs and resuming their own chats resolve `task.<task id>`, which inherits the main-chat category until that task is given its own launcher / model / effort. An override is written through `PATCH /api/v1/model-config/purposes/task.<task id>` (sparse, revision-checked) or the `schedule_routine` / `schedule_followup` `launcher` / `model` / `effort` arguments, and is validated against the machine that starts the task's new runs. Its record lives under `model_config.overrides.v1.task.<id>`, so the dormant pre-#1570 `model_config.task.<id>` records never revive, and deleting the task clears it. The override applies when a run starts or continues the task's own conversation; a run sent into the conversation the task came from keeps that conversation's launcher, so the tools refuse a task's own launcher for a follow-up that continues its source conversation (`new_conversation: true` gives it one). A model or effort given without a launcher pins the launcher the task runs on at that moment, so a later Main chat change cannot pair the model with another agent. Messages the user sends into that task's conversation, and follow-ups sent back to it, still follow “Main chat” for every message, just like the main chat, rather than retaining the previous turn's launcher. Returning to a source chat (a follow-up the assistant schedules for itself with `schedule_followup`) is a turn in that assistant chat, using the same rules as phone messages: the main chat and scheduled tasks' own chats use “Main chat”; the assistant's other chats retain their running launcher and model (#1518: previously classified as Agents, a follow-up switched the main chat to default Claude Code, which was not logged in on the hub machine; every later message returned `Not logged in`). Task permissions, run history, and session associations remain unchanged. GET for old purposes returns read-only information; PATCH is rejected. Apple's old purpose-editing links open the owning category editor and explicitly explain that changes apply throughout the category. Old hubs without the four-category catalog prompt for an update rather than pretending different effective models are four category defaults.

## Who owns models (2026-11-05)

Model configuration belongs to the **manager** (the assistant process `personad assistant`, `docs/assistant/assistant.md`, “Boundary with hub”). hub neither uses models nor stores model configuration:

- The manager owns: the four category records `model_config.*`, providers added in Persona and their sealed keys (settings `launchers.managed`), hidden ~/.zshrc launchers (`launchers.hidden`),
  each computer's last reported ~/.zshrc launchers (`launchers.zshrc`; offline computers still show their last report), presets, and rate-limit pauses. Code lives in `server/internal/assistant/models*.go`. Keys and tables are unchanged; no data migration.
- Routes: CRUD for `/api/v1/model-config…`, `/api/v1/launchers`, and `…/check`, `…/restore`, `/api/v1/launchers/presets`, `…/quota`, `…/test`, `…/discover`, `…/import`, plus the new-Agent picker
  `GET /api/v1/machines/{mid}/launchers…`, belong to the manager (`assistantwire.Routes`). hub forwards them unchanged: paths, fields, and errors stay the same; no app changes needed.
- Every model consumer calls the manager's own configuration directly: triage, assessment, drafting, translation, knowledge, titles, Agent label names and triage, new Agents (`applyModel`), and Agents opened from Lark cards.
- The manager names Persona-added launchers to the computers in each one's device scope (after changes, when it connects, or when a node connection is new, `launchers.catalog`; `launchers.managed` for old nodes), and a node fetches a provider's key when it needs it (`launchers.pull`, `docs/integrations/launchers.md` "Device scope and on-demand delivery"). Keys pass through the manager's connection to the node; hub neither stores nor decrypts them. A launcher purpose bound to a computer (the main chat's) cannot pick a provider out of that computer's scope, and its status says why when one picked before the scope changed is still set.
- The legacy baseline is the manager's own: `ai`, `kb.ai`, `inbox.triage_ai` / `judge_ai` and `inbox.agent.machine` come from its `manager.json` (`docs/operations/config.md` ("manager.json")). hub supplies only the facts it knows: each computer's `machines[].launchers` from hub.json
  arrive with the handshake (`models.launchers` in `manager.hello`'s answer, `manager.updated` on changes). Inheritance rules remain unchanged. The manager queries plugin provider presets, voice-plugin models, and which enabled plugins need “Information screening”
  through `app.call plugins.presets` / `plugins.voice` / `plugins.quota` / `plugins.need_triage` (these three are removed after the plugin system moves into the manager).
  `api_key_file` is a path read by the manager on its own machine: the default child process runs on the same computer as hub, as the same user, so it can still read it.
- The manager answers the two questions hub plugins need: whether “Information screening” is currently callable (`models.usable`, governing whether dependent plugins can be enabled), and requests that quota plugins or plugin launcher panels need to send with a key
  (`models.launcher_http`: the manager sends with keys for Persona-added providers; for ~/.zshrc providers, the computer's node sends, and the key never leaves that computer). The quota route `…/launchers/{name}/quota` and its one-minute cache also belong to the manager: it selects the gateway and machine, asks hub's quota plugin to read (`app.call plugins.quota`), and requests the plugin needs to send return to the manager through `models.launcher_http`.

**Key encryption**: `server/internal/secretkey`. The built-in manager uses its own `secret.key` (`~/.persona/managers/assistant/secret.key`, copied once from `~/.persona/secret.key`, the file the hub sealed the keys with before they were the manager's, so existing keys remain decryptable; [managers.md](managers.md) ("The built-in manager's own files"))
to seal and decrypt provider keys. It creates the file if missing (even if both processes create it simultaneously, only one writes successfully). hub's own secrets (Lark bots, connectors, plugins, linked-hub credentials) still use the same file and package, but hub does not touch provider keys.
If the manager runs elsewhere (`assistant.external`), copy the hub machine's `~/.persona/managers/assistant/secret.key` to the same place on that computer (0600) before the manager first starts there: once it has started it has a key of its own, which a copy put in `~/.persona` afterwards does not replace. Otherwise old keys cannot be decrypted; status says “Provider key decryption failed,” and the user can re-enter the key in Settings › Model Providers.

**When the manager is unavailable** (restarting, or the `assistant.external` computer disconnects): the routes above return `503 assistant_offline` and resume normally when it returns. Configuration lives in Postgres and survives both hub and manager restarts.
Quota returns `503 assistant_offline`; plugins needing “Information screening” cannot be enabled (same error), and such plugins configured in the manager's manager.json do not receive items yet. Model-powered features already live in the manager and stop with it.

## Who resolves the Agents category (2026-11-04)

Choosing the launcher and model for a new Agent is part of Agents and belongs to the **manager** (assistant process, `docs/assistant/agent-work.md`, “Responsibilities”). Before `POST /api/v1/sessions`, hub asks it for
`agents.start_params`; before sending to a stopped session whose launcher is unknown, hub asks for `agents.resume_params`. Agents dispatched by the assistant itself (`agents_start`, tasks) already live there.
It resolves from its own model configuration (`applyModel agent.new`: category choices, overlaid by the launcher / model / thinking effort selected for this run, and the execution fingerprint). The app's effective result, saving, and inheritance remain unchanged.
Agents is the one launcher purpose with no computer, so the result is then held to what the target computer has (#2640, `docs/server/launcher-health.md`, "A launcher the computer doesn't have"): a default it lacks gives way to `claude` (or its first launcher), a launcher picked for this run that it lacks is refused (400) with the ones it has.
Label names (purpose `agent.title`) and session triage (`agent.triage`) also call models there.

When the manager is disconnected, hub waits only if it has just started and the manager has never connected (at most until 60 seconds after startup). Once it has connected and is now absent, hub does not wait: the manager connects computers (`docs/server/machines.md`, “Who connects to computers”),
so creating or resuming sessions is impossible without it and returns `503 assistant_offline` (previously hub could apply “Model Settings › Agents” itself and still start them). AI twin execution opens on the assistant side through `assistant.start`, so resolution already happens there; Agents opened from Lark bot cards also live on the assistant side (it owns channels).

## Main-chat runtime (#2455)

“Main Chat” adds “Runtime”: `cli` (default, `claude -p` streaming JSON) or `agentsdk` (through an Agent SDK bridge, `docs/integrations/claude-integration.md`). Only `assistant` has this setting; scheduled tasks follow it (inheriting main chat). Agents and API purposes do not accept it; PATCH returns 400 if it is included.

- Stored in the binding of `model_config.assistant` (`runtime`), independent of provider and model: changing providers, temporarily choosing a launcher or model in the chat menu, or prewarming another launcher still uses this runtime.
- `finishModel` puts it in params sent to node (`runtime: "agentsdk"`; omitted for CLI) and includes it in `model_fingerprint`. A change makes node restart the process and resume the original session with `--resume`. Explicit `cli` and omission produce the same fingerprint, avoiding unnecessary restarts.
- If node cannot run the SDK (no Node 22+, bridge, or claude), it falls back to CLI and includes `runtime_fallback` in session status.
- A binding without a model means the launcher's default, on a resume too (#2487). Claude Code resumes a session on the model it last ran on unless `--model` or a model variable (`ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_*_MODEL`) names one; a `model` in its settings does not. So when node resumes a conversation the hub resolved with no model, it passes what a new session of that launcher would use: the `model` from Claude Code's settings, else `default`. It passes nothing when the launcher names a model itself or when its start cannot be seen (a managed launcher, a wrapper script); see `node/assistant_resume_model.go`.

## A conversation's own model (#5033)

The model panel of a Persona chat switches that conversation to another launcher, model or reasoning effort, and the choice stays with the conversation: its next messages run on it, on every device, until the user switches again or goes back to the default (the user's ask on 2026-11-12). Model configuration › Main chat stays the default: a conversation without a pick follows it (the main chat and a scheduled task's own conversation) or keeps what it runs (the others), as before.

- **Kept on the hub side** (`assistant/model_pick.go`): `PUT /api/v1/assistant/conversations/{id}/model` `{launcher, model?, effort?}` keeps the pick in the manager's settings `assistant.model_picks` (Postgres, by session id with its computer; at most 512, the oldest go first but never the main conversation's; a change is computed under the book's lock and written outside it, so reading the picks never waits on the database); `DELETE` on the same path goes back to the default. Assistant conversations are never deleted (they archive, and `DELETE /api/v1/sessions/{mid}/{sid}` refuses them), so an archived one keeps its pick for when it comes back. Every device sees it as `model_pick` on the conversation (absent: it follows the default), so a client can tell "the default" from "picked for this chat" and offer a reset. Feature `assistant_model_pick`; an older hub keeps nothing, and the apps send the pick with each message there as before. API details: `docs/protocol/protocol.md`, "REST (App → hub)".
- **Picked when the conversation starts**: `POST /api/v1/assistant/conversations` takes `launcher`, `model` and `effort` for the first message, checked like a message's pick (a model ID, typed ones kept; refused for a launcher that sets its own model or takes none, before anything starts), and keeps what was named as the new conversation's pick when it named a launcher or a model (a start under another purpose or a guest conversation keeps none). An effort alone keeps nothing: iOS sends its last effort with every start, and that must not tie a new conversation, a new main one least of all, to the default launcher of that moment. A launcher that isn't on the computer still falls back to the default as before, with its model dropped, and no pick is kept then. An older app that sends only `launcher` now gets that launcher kept for the conversation too.
- **Applied to every message that picks nothing** (`sendModel`, `sendOnPick`, `applyPick`): the pick's launcher, model and effort, checked and fingerprinted like a message's pick (`applyPickedModel`, on the main chat's runtime); an effort sent with the message wins over the pick's. A pick without a model runs what its start ran: Model configuration › Main chat's model when the launcher is the one configured there (and that model's later changes), else the launcher's own default (`applyModel`). An effort the apps set later through `POST …/modes` (#2416) becomes the pick's effort (the manager sees the hub's `session.modes` call go through, `nodeCallDone`), so the next message doesn't put the old one back. A launcher or model sent with the message (an older app) still wins for that message, as before. A scheduled task's follow-up into the conversation and a rich view's message run on the pick too, and `POST /api/v1/assistant/warm` with no launcher warms the main conversation's pick, on the main conversation's machine.
- **Clearing and new main chats**: `/clear` ("Clear context", #5095) starts the main conversation over under a new session id; its pick goes with it (`mainHandoff.pick`, kept when `/clear` comes again before a new main conversation started): the next main conversation starts on it and keeps it, unless that start names its own launcher or model. That start is held to what a message on the pick is held to: a pick that can't run there any more refuses it once with the same codes (409 `launcher_out_of_scope` / `launcher_own_service` / `launcher_missing`, 400 when the launcher can't run assistant chats or its model can't reach the agent) and is dropped, so the next start runs on the default; it never falls back silently. The start's own effort (iOS sends its last one with every start) is the first message's only; the pick keeps its own. `POST /api/v1/assistant/warm` with no launcher warms the carried pick until then. "New main chat" (`POST /api/v1/assistant/main/new`) is a fresh start: the new main conversation follows Model configuration › Main chat, the old one keeps its pick in the archive, and after `/clear` it drops the carried pick.
- **Limits**: picks are this manager's, for its own conversations on its own computers; a conversation on a computer another manager carries keeps none here. A start keeps its pick right after its first message was handed to the computer, so a second message sent in that moment runs as if there were none.
- **Never replaced**: when the default's launcher can't run here, the hub falls back to one that can (`finishMainChatModel`, unchanged). A pick is the user's choice, so a message on one that can't run any more is refused with why, and the pick stays until the user changes it: a provider out of the computer's device scope or skipping a computer with its own sign-in (409 `launcher_out_of_scope` / `launcher_own_service`, the scope's words), a launcher gone from the computer (409 `launcher_missing`, worded by the hub with the "connect a model" action), or one that can't run assistant chats (400). A launcher of the other agent kind than the conversation's (Claude Code can't resume a Codex thread, nor Codex a Claude transcript) is refused with 409 `launcher_other_kind`, as a message's own pick is (`launcher_kind.go`). The PUT refuses the same before keeping anything. With the computer's launcher list unreadable nothing is refused on a guess (`mainChatFit`).
- **What a pick can be**: a launcher the computer's main-chat picker lists (`GET /api/v1/machines/{mid}/launchers?purpose=assistant`: its rc-file aliases and PATH wrappers, plain `claude`, and the Model providers that can run the main chat, launchers and Messages-protocol direct APIs, within the computer's device scope); a model that is a model ID (`proto.ValidModelID`), refused for a launcher that sets its own (`locked`) or whose agent takes none, and kept when the launcher's list lacks it (a typed one, "Typing a model ID"); an effort that is `auto`, one of Claude Code's levels or one of Codex's.
- **What can't, and why**: `?purpose=assistant` also answers `unavailable`, so the panel shows these disabled with the reason rather than hiding them: the computer's launchers that can't run assistant chats (`not_main_chat`: a Paseo provider, a managed Codex launcher, a runtime without the assistant capability), then the Model providers that can't run here: Responses / Chat Completions direct APIs (`api_protocol`), an agent that can't (`not_main_chat`), out of the computer's device scope (`launcher_out_of_scope`) or skipping it for its own sign-in (`launcher_own_service`). Reasons come in the request's language; hidden launchers stay out entirely.
- **Typed IDs**: the hub remembers a typed model (`models.used`, "Typing a model ID") when a message carried it. A pick's model is not sent with the messages, so a typed model kept only as a pick is not offered again under "Typed before" until a message carries it.

## Importing providers from shell aliases (#2455, #5024)

`GET /api/v1/launchers/import?machine=` previews; `POST` confirms (see `docs/protocol/protocol.md`, “Model providers and per-purpose configuration” for the API). The manager calls that machine's node `launchers.zshrc` (`assistant/models_import.go`), which reads `~/.zshrc` (`$ZDOTDIR` first), `~/.bashrc` and `~/.bash_aliases` in the login shell's order (zsh: `~/.zshrc`, `~/.bashrc`, `~/.bash_aliases`; bash: `~/.bashrc`, `~/.bash_aliases`, `~/.zshrc`). Each alias says which file it came from; a name defined in two files is read from the first of them in that order (inside one file the last definition counts, as in the shell). The manager then merges them with the pure function `mergeZshrcAliases` (same file):

- One `ANTHROPIC_BASE_URL + key` group (`ANTHROPIC_AUTH_TOKEN` first, using bearer; otherwise `ANTHROPIC_API_KEY`) is one provider. Name and other settings come from the first alias; every alias's `ANTHROPIC_MODEL` is merged into `models`. Entries without a gateway address (ordinary Claude Code) are skipped.
- **Aliases that differ.** A group of two or more aliases also carries `variants` (each alias as a provider of its own: its name, settings, its model) and `differs`, what the aliases set differently apart from the model (`tiers`, `effort`, `args`, `limits`, `proxy`, `headers`, `env`, `auth`, `custom_model`; `importSettings`). `POST` with `split` imports such a group as its variants; without it the group is merged and only the first alias's settings are kept. A merged provider stands in for every alias of the group, so when the user picks “One provider” for aliases that differ (the dialog says the others keep only their model), the others are checked and hidden like the first. A variant lands in a stored provider only when that provider has the same `base_url + key` and was imported from the same alias (`source` `zshrc:<alias>@<any computer>`); a merged group lands in any stored provider with the same `base_url + key` (`existing`), which gets only the new models; its other settings in Persona take precedence.
- Model names ending in `[1m]` lose the suffix and record a context window of 1000000 (node adds the suffix back at startup according to the window). `ANTHROPIC_CUSTOM_MODEL_OPTION`, `_NAME` and `_DESCRIPTION` fill the provider's custom model fields.
- **Environment** (`models_import_env.go`). Variables with a field fill it and never go into `env`: the base URL, key and token, `ANTHROPIC_CUSTOM_HEADERS`, the model and tier models, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`, `CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_CODE_MAX_CONTEXT_TOKENS`, `API_TIMEOUT_MS`, the custom model option and every spelling of `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY` (`proxy` is the first of `HTTPS_PROXY`, `https_proxy`, `HTTP_PROXY`, `http_proxy` that is set; `no_proxy` is `NO_PROXY`, else `no_proxy`). The others go into the new provider's sealed `env` as `NAME=value` lines sorted by name, quoted with `"…"` when the value has a blank, `#` or a quote and with `'…'` when it has a `"`, so the node's `envLine` reads back exactly the value. Left out, each named in the preview's `skipped_env` with its reason:
  - `credential`: a name with an underscore-separated word (any case) KEY, KEYS, APIKEY, TOKEN, SECRET, SECRETS, PASSWORD, PASSWD, CREDENTIAL, CREDENTIALS, COOKIE or COOKIES (`CLAUDE_CODE_MAX_OUTPUT_TOKENS` is kept), or a value with a user in it: its authority (after an optional `scheme://` or a leading `//`, up to the first `/`, `?` or `#`) has an `@`, or it does not parse as a URL and has an `@` anywhere. That catches what Go's URL parser refuses but Claude Code takes (`http://user:Ab^9{x@proxy.example:8080`), `user:pass@host:8080` without a scheme and `//user:pass@host`; an e-mail address is left out too, on the safe side. A proxy with a user, in any of the four spellings, is left out this way and leaves `proxy` empty: the proxy is stored and shown in the clear.
  - `shell`: a value with `$` or a backquote, or starting with `~` (Persona stores text, not what the shell would expand), or one no env line holds (a line break, NUL, both kinds of quote).
  - `computer`: `PATH`, `HOME`, `PWD`, `OLDPWD`, `SHELL`, `USER`, `LOGNAME`, `TMPDIR`, `CLAUDE_CONFIG_DIR`: the provider runs on every computer in its scope.
  - `limit`: beyond the 50 lines an env takes (`checkEnv`).
- Preview includes neither keys, request headers nor env values, only `has_key` / `has_headers` / `has_env` and the names (`env_names`, `skipped_env`). On confirmation, the manager rereads them; keys, request headers and env pass only through the manager and are encrypted at rest like manually added entries.
- A created provider is named after its alias (a group: its first alias), but never with a name Persona already lists: the alias itself (listed from the rc file), a launcher of another computer or a stored provider; it gets `-2`, `-3`… The preview's `create_as` says that name. One rule names both (`importNames`): groups in the preview's order, a group and its variants each against what earlier groups may take (merged or split is the user's choice), and every name a group may take taken for the groups after it. `POST` works the names out again under the configuration lock and saves under them, so they differ from the preview only when something changed in between; `name` stays the group's identifier for `POST`.
- A created provider is `own_service: use`: the alias makes its computer count as having a Claude service of its own, so `skip` would keep the provider off the computer it came from. Its share and delivery are a new provider's defaults (every computer, on demand).
- **Hiding the imported aliases** (`models_import_hide.go`). After an import the alias and the provider made of it would both be listed, so `POST` with `hide_aliases` adds each imported alias whose check is `ok` to `launchers.hidden` (Settings › Model providers › Hidden restores it; the shell files are never touched). The preview's `sources[].hide` and the import ask the same question, `aliasHide`, against the provider the alias lands in (created, a variant's, or `existing`); the import asks again under the configuration lock, against the provider list it is about to save, and changes no purpose, task, profile or Agent preset. The preview reads what the check needs only when Persona lists one of the aliases, and never fails over it: when the tasks, profiles or model records cannot be read, every alias is `none` (logged). The import with `hide_aliases` refuses instead, writing nothing. It reads `launchers.hidden` again under the lock and writes it with the providers in one transaction (hiding and restoring an rc-file launcher take the same lock); with a store that writes one setting at a time, the providers go first and a failed hide answers 500 saying they were imported but the aliases were not hidden:
  - `none`: Persona does not list that name (no computer's rc-file list has it the way Settings › Model providers lists one), it is already hidden, or it is `claude` / a reserved name.
  - `in_use` (stays, `uses` says what in words): a current purpose names it (`providerModelUses`, extensions' purposes included), a scheduled task's own record does, a saved model profile's purposes do (in use or not), or a profile's Agent preset runs on it. Hiding it would move a start to another launcher (#4661).
  - `elsewhere` (stays, `elsewhere` names the computers): a computer that lists the alias would not get the provider in its place with the same account: out of the provider's scope (`scopeReason`, a work computer for a new provider); every computer when the provider is `own_service: skip` (the alias stays in the file, so the computer keeps counting as having its own service); a computer for which the provider has a key of its own (`machine_keys`) other than the alias's key; or another computer whose own alias of that name does not reach the same base URL (after `proto.MessagesBaseURL`) with the same key (`ANTHROPIC_AUTH_TOKEN` without `Bearer `, else `ANTHROPIC_API_KEY`). The manager asks each such computer's node for its aliases (`launchers.zshrc`, once a request, at most 5 seconds) only for an alias nothing uses; the import asks before it takes the configuration lock, and its check under the lock reads only those answers (a computer not asked then counts as `elsewhere`); offline, a node too old to answer, an error, no alias of that name there (a shell function, say) or another address or key all count as `elsewhere`. The keys are compared in the manager and never logged or returned.
  - `ok` otherwise.
- A body without `split` and `hide_aliases` (iOS, Android, older web clients) merges every group and hides nothing; the env passthrough and `own_service: use` apply to every import.

## Launcher-picker defaults

`GET /api/v1/machines/{mid}/launchers` includes `default: {provider, model, effort, runtime?}`, the effective value for the corresponding purpose in “Model Settings” (`?purpose=`, default `agent.new`; the main-chat picker sends `assistant` and gets an extra `runtime`). Clients use it to show “Default: …” without separately querying model configuration.

## Choosing a model for a new Agent (#794)

After choosing a launcher for a new Agent, select this run's model from the “Model” list. It is the same list shown by `/model` in the terminal when that launcher runs Claude Code / Codex on this computer.

- **Ask the CLI, not configuration files**: settings.json, config.toml, and launcher environment variables contain only defaults and gateway addresses. The CLI combines its own aliases with the gateway's `/models` response; parsing configuration yourself misses variables set by ~/.zshrc launchers and alias mappings. node starts the CLI once using the launcher as-is (`node/launcher_models.go`): Claude Code receives an `initialize` control request in headless streaming-JSON mode; the response's `models` is the `/model` menu (default / opus / sonnet / haiku resolve to actual models under this launcher's settings, plus every gateway model). Codex uses `model/list` from `codex app-server` (paginated, excluding `hidden`). Kill the entire process group once the list arrives; no messages are sent and no model is called. This Claude run uses `disableAllHooks` (merged with the launcher's own `--settings`), so neither Persona nor user hooks mistake it for a session start.
- **Cache**: node caches by “launcher + managed-launcher settings” for 10 minutes, sharing one CLI invocation across simultaneous requests. After that, a list up to 24 hours old is still answered at once while the CLI is asked again in the background, so the picker does not wait for it every ten minutes (#1501). `?refresh=1` (pull to refresh or retry after an error in the app) asks again and waits. Measured: about 4 seconds for Claude Code, under 1 second for Codex.
- **Ordered assistant fallback**: for the bounded transient recovery in [claude-integration.md](../integrations/claude-integration.md) ("Headless assistant"), this list's order is also the order in which node tries later models after the current model's one same-model retry. Effort follows the fallback model: an unsupported level resets to the launcher's default, as in the picker. This list is not a new routing configuration and is unrelated to ModelProfile.Tiers' named Agent presets. An unavailable list or a `locked` launcher means no model switch; it never turns `default` into a second request or silently picks a different launcher.
- **Can the selection take effect?** `launcherModelCheck` (`model_probe.go`) also checks whether the launcher forwards `--model` unchanged to the CLI. Launchers hardcoding `--model` return `locked`; the app locks the model row, explains why, and omits the model (node rejects startup if one is sent anyway).
- **This run only**: the selected model travels in `model` on `POST /api/v1/sessions`, overriding “Model Settings › Agents” (`applyModel`). node adds `--model` when starting the CLI (both Claude Code and Codex). It does not change global defaults (a model ID the user typed is offered again in the list, see “Typing a model ID”); changing machine or launcher resets to “Default model.” “Default” means no model is sent: use the launcher's own default, or the configured model when the launcher is the one in “Model Settings” (the app's second line says “Model configuration: …”).
- **Thinking effort follows the model**: each Claude model includes its supported levels (only low…max understood by node are retained). The app lists only these; if the current choice is unsupported, reset to “Follow launcher.” Models without levels cannot select thinking effort (the control is disabled or marked unsupported). With no model selected, use the model that will run: the “Model Settings” model (if its ID is absent from the list, treat support as unknown and list all levels), otherwise the default model. New Codex sessions do not send thinking effort (“When changes take effect” above).
- **Without a list**: an internal Codex fork and runtime launchers (DSH…) return `models: []`; the app hides the model row. Old hubs return 404 and also hide it; if hub is new but this computer's node is old, hub returns 404 too (`code: node_outdated`), avoiding a retry that will always fail. If listing fails (CLI missing, not logged in, timeout), the model row shows the reason and retry, while “Default model” can still start.

## Choosing a model in model configuration (#943)

When a Claude Code / Codex launcher provider is selected in “Model Settings,” “Specific model” also selects from that launcher's `/model` list, using the same list and picker as new-Agent creation (web `ui/ModelPicker.tsx`, Android design-system `JModelSheet`).

- **Which computer is asked**: Model configuration belongs to the manager, not a computer. `GET /api/v1/model-config/providers/{id}/models` chooses an online computer with this launcher and asks node's `launchers.models`: the one specified by `?machine=`, the assistant's computer, the local hub computer, then the others, in that order (`pickMachine` in `assistant/models_launchers_routes.go`). ~/.zshrc launchers exist only on the computer defining them; Persona-managed launchers (`personad launch`) run on every computer in their device scope, and “Claude Code default” on every computer. The response includes `machine`, and the page identifies the source computer.
- **“Default” means empty**: Empty here means inherit. If neither provider nor model was selected, the “Default” row shows the inherited model (the one under “In Effect”); with a selected provider, it shows that provider's default model (the list's default entry).
- **IDs outside the list still work**: The list may be incomplete (new gateway models, different settings on other computers). If the ID entered in search has no exact match, add a “Use ‘…’” row. Already-configured models outside the list still appear, marked “Not in list.” Saving remains separate from paid-availability testing.
- **Without a list**: Plugins use their own lists (as before); API providers have no list. Old hubs, outdated nodes (404), or listing failures fall back to the original text field, with the failure reason and “Retry” below.
- Thinking effort: the web client lists only levels supported by the selected model; Android still uses free-form input.

## Typing a model ID (#1644)

The `/model` list is not every model a launcher can run: a gateway behind a `~/.zshrc` launcher serves its own models while Claude Code lists only its tier aliases, and a new model can be newer than the list. Claude Code's `--model` / `/model` and Codex's `--model` take any string, so New Agent, a running session's model switch and the Persona chat's model chip also take a typed model ID (the apps' entry is the clients' part of #1644; this section is the hub's).

- **One rule everywhere**: `proto.ValidModelID` (`server/internal/proto/modelid.go`): a letter or digit first (or `~` and then one), then only letters, digits and `. _ - / : @ [ ]`, at most 256 bytes. That covers aliases (`opus`), variants (`opus[1m]`), a gateway's `vendor/model` and its "latest" aliases (`~vendor/model-latest`, `~vendor/model-latest[1m]`), tags (`qwen3:32b`), dated IDs (`claude-x@20250101`) and ARNs, and keeps out whitespace, control characters, quotes, `$`, backticks, `;`, `|`, `&`, globs and a leading `-`. Checked by the node before anything runs (every start's `modelExecution.check`, the launcher check, the `/model` line typed into a running Claude Code, all answering `invalid model`), by the manager for New Agent's pick and every launcher binding (`applyModel` / `finishModel`), Model configuration's launcher purposes (400), a Persona chat message's pick (`sendModel`, 400), and the assistant's `agent_start` / `task_plan` and a plan card's edit (400) before anything is asked or started. Refusals are said in the App's language: the hub passes the request's language to the manager (`lang` on `agents.start_params` / `assistant.send_params`).
- **Configured before the rule**: a launcher purpose saved with a model that breaks the rule (the old check only refused line breaks, NUL and over 512 bytes) is not passed on: its runs take the launcher's default and the manager logs it, so the main chat, `assistant.warm` and the other purposes keep working. Editing that purpose is refused naming the model until it is cleared or replaced (the node's model check would refuse it anyway).
- **Quoted on every command line anyway**: herdr's start command (`shellQuote`), the resume command herdr runs after a restart (`dquote` inside `eval`), the launcher probe (`shellQuote`), so a leading `~` is never expanded to a home directory; the assistant CLI gets it as a separate argument (`"$@"`), Codex and managed launchers by exec. `node/model_inject_test.go` runs those command lines in a real shell with hostile strings and checks the agent gets exactly one argument after `--model` and nothing else runs.
- **The Persona chat keeps a typed pick**: a model picked with the message is no longer dropped because the launcher's list doesn't have it. Only a model carried over from what the conversation ran is still held to the list (or to the IDs typed for that launcher before), so a model the gateway dropped doesn't fail every later turn; a carried-over value that isn't a model ID (Claude's `<synthetic>`) is not carried.
- **Remembered per computer and launcher, for every device**: once a start (`POST /api/v1/sessions` with `model`), a running session's switch (`POST …/modes` with `model`) or a Persona chat message with a picked model went through, the hub tells the manager (`models.used {machine_id, launcher, model}`, best effort). A start the node answers before it runs (`async`, what the apps' New Agent sends) counts only once the session is listed as started (no longer `starting`, no `start_error`; the hub watches its list for up to 10 minutes, `modelUsedOnceStarted`), since the launcher's model check and the agent coming up happen after the answer; a synchronous start counts when it returns. The manager keeps it in the settings key `launchers.custom_models` (Postgres) unless the launcher's own list has it (an ID or what an alias resolves to) or the launcher takes no typed model (`locked`, or an agent other than Claude Code / Codex); with the list unknown it is kept. Most recent first, at most 8 per computer and launcher, 256 in all. A start that failed, a refused request, or a model the assistant chose itself (`agent_start`, `task_plan`) is not remembered. "Went through" means the agent took the ID, not that the model answered: Claude Code takes any `--model` / `/model` string and only fails on the first API call, so a mistyped ID that started is remembered until the user forgets it (below).
- **Offered in the lists**: `GET /api/v1/machines/{mid}/launchers/{name}/models` (and Model configuration's `…/providers/{id}/models` for the computer it asked) appends them after the CLI's own entries as `custom: true` with a short description and no `efforts` (unknown: the apps offer every level or leave it to the model). A list of a launcher that takes no typed model (another agent's empty list, which tells the apps to hide the model row; a `locked` launcher) gets none. They count for the carried-over check above. Older apps just see more rows.
- **Forget**: `DELETE /api/v1/machines/{mid}/launchers/{name}/models/custom?model=<id>` drops one (idempotent). Forgetting doesn't stop a running session or change any configuration.
- Launchers that hard-code their own `--model` stay `locked`: a typed ID is refused like a listed one. Switching the model of a running Codex session is still not supported.

**In the apps** (iOS / Mac / visionOS and the web; Android later):

- **Same rule, said as it is typed**: `apple/Shared/ModelID.swift` and `web/src/lib/model-id.ts` mirror `proto.ValidModelID` (tested on the server's cases) and name the first thing wrong (empty, how it starts, a space, a control character, the character that isn't allowed, over 256 bytes) under the field; "Use" stays off until the hub would take it. The spaces and line break around a pasted ID are dropped.
- **New Agent**: "Other model…" at the end of the model list (iOS: a sheet with the field, `TypedModelSheet`; web: the field in the list, `ModelIdField`), and the search takes a typed ID too ("Use “…”", or why not). When the list is empty or couldn't be read (Claude Code / Codex only), the row is "Enter model ID…" beside the error and Retry; on iOS a pick typed there has a clear button back to the default. Its efforts aren't known, so every level is offered. Locked launchers keep the locked row (an empty list too) and send no model.
- **IDs typed before**: listed under the launcher's own models ("Typed before", drawn monospaced as typed; the heading says what they are, so the hub's description isn't repeated on each), with Forget (iOS: swipe or the context menu; web: × beside the row) calling the DELETE route: the row goes at once and comes back, with the hub's reason, when it refuses (`LauncherModelsModel.forget`, web `withoutCustom`; the web popover keeps its pick by ID, so a refused Forget doesn't move it).
- **A running Claude Code session**: "Other model…" in the model menu (the shell composer's, the old layout's thinking chip, BeautifulUI's prompt bar) opens the field with the session launcher's typed IDs; a pick goes through `POST …/modes {model}` (the node's guards), never as a `/model` message (`PromptItems.modelPick`). The web popover has the row in its model list: a good ID is staged as it is typed, so its Apply (or Enter) is the one confirm; the list shows what was read last at once and is read again behind it. - **The Persona chat's launcher menu**: each Claude Code / Codex launcher's submenu lists its typed IDs after its models and ends with "Other model…" (iOS: the sheet, which also lists and forgets the typed IDs; web: an input row in the menu, plus "Forget a typed model"); the pick is the next messages' model like a listed one. ## When changes take effect

- API purposes resolve configuration at the start of the next call; knowledge uses injectable per-purpose models rather than freezing the old object at hub startup.
- The specific primary model for chats and Agents is passed through CLI arguments or the Codex app-server model field, not just environment variables that a launcher may clear.
- Prewarming / process reuse carries an execution fingerprint, so a launcher with the same name but changed model or credentials does not reuse a stale instance.
- Saving does not kill the current turn or background tasks. If a process switch is needed while still busy, reject the switch and retry at a safe boundary; do not claim lossless Claude/Codex continuation across executors.
- Historical triage is not rerun, and existing knowledge is not rewritten. Translation caches distinguish model configurations so the next translation cannot reuse a cache from the old configuration.
- New Agents default to “Follow model configuration”; a manually chosen launcher overrides only this run. The client's last-selected launcher no longer automatically overrides global configuration. Claude Code and Codex retain their own creation paths; Codex requires a first message, explicitly overrides the model with `--model`, and keeps thinking effort under its own launcher rather than mixing in Claude's permission/thinking arguments.
- Voice models are read only when the next voice session starts/restarts. A legacy hub 404 permits reading old client defaults for compatibility; a read failure on a new hub must not be treated as missing configuration and trigger fallback.
- Model changes neither change permission mode nor authorize automatic message sending.

## Upstream rate limits

Direct-API purposes (knowledge processing, Inbox triage / assessment / drafting, translation, titles) all run in the manager and share the client in `server/internal/ai`. Each connection (address + key, regardless of purpose) has its own gate (`ai/limit.go`):

| Upstream response | Interpreted as | Pause behavior |
| --- | --- | --- |
| HTTP 429, body mentions quota / usage limit / exhausted, etc. (relay `account_quota_exhausted`) | Quota exhausted | Pause for 30 minutes; honor `Retry-After` if present |
| HTTP 429 / 503 mentioning concurrency (`account_concurrency_full`), or other 429, 503, 529 | Concurrency full | Exponential backoff (starting at 5 seconds, doubling on each consecutive occurrence, up to 5 minutes); use `Retry-After` if longer, and add a concurrency cap for this connection |

- **Every call streams**: Messages, Responses and Chat Completions requests all ask for a stream (`"stream": true`), so a gateway's cap on a non-streamed request's total time (often 120 seconds) does not fail an answer a slow model needs longer for (#4245). A Messages server that ignores the flag and answers one JSON message is read as before. A stream that ends before its end event (Messages: `message_stop`, or at least a stop reason; Responses: its terminal event; Chat Completions: the finish reason) was cut: it is a failed connection, retried like one, not a short reply.
- **Limits reported inside a stream**: A Messages `error` event whose type is `overloaded_error` or `rate_limit_error` counts as concurrency full (the HTTP 529 / 429 it stands for; a `rate_limit_error` whose message speaks of quota or credit as quota exhausted). A Responses `response.failed` or `error` event after the 200 whose code is `rate_limit_exceeded`, `slow_down` or `server_is_overloaded` counts as concurrency full, and one whose code is `insufficient_quota`, `credit_balance_exhausted`, `organization_spend_limit_exceeded` or `project_spend_limit_exceeded` as quota exhausted, with the wait in a "try again in ..." of its message (`1.5s`, `250ms`, `20 seconds`, `6m0s`, `1m30s`) used like `Retry-After`; any other in-stream failure is an ordinary error.
- **No requests during a pause**: Calls immediately receive `ai.PausedError` (`ai.IsPaused`), with the same text displayed in the app: “Quota exhausted; retry in 23 minutes.” Callers treat it as deferred: knowledge-processing loops stop immediately (sessions remain pending compaction, projects pending rewrite, entries untagged); Inbox triage does not mark entries as triaged (new entries go into rule-based groups first and are triaged again after recovery); assessment and translation wait for the next round. None logs it.
- **Only the gate logs**: One line on entry (address, upstream code and message, pause end time), one on exit (pause duration, number of deferred requests).
- **Release one request after the pause**: The first request probes recovery; others remain deferred. Only a successful probe opens the gate; another rejection starts a new pause (without another log). Matching responses from requests already in flight before the pause do not count and do not compound the backoff.
- **Concurrency cap**: On the first concurrency-full response, set it to half the current in-flight count (at least 1); halve it again on another full response. Then increase by 1 after every 10 successes; stop limiting once it exceeds 8. Requests above the cap queue for a slot until their own deadline; reaching it also counts as deferred. The knowledge base loop's calls are marked background (`ai.Background`): they queue for at most 30 seconds, or until their own deadline if sooner, and are then deferred without being sent, so they give their turn back instead of spending their whole deadline (minutes) in the queue, while a call someone waits for on the same connection keeps waiting (#4246).
- **Visible in the app**: In the model-configuration API, purposes whose connection is paused carry `limit` (`reason`: `quota` / `busy`, `until`), and `status` is the text above (apps, web, and Android versions that do not understand `limit` still show it).
  The app displays a warning in purpose rows and details under “Settings › Model Settings” (a `Theme.caution` symbol + `cautionText` text), counting down from `until` while the page is open. Screenshots use mock `MOCK_MODEL_LIMIT=1`.

## API

`purposes` in `GET /api/v1/model-config` returns the five ordered category configurations followed by the editable AI twin (`inbox.agent`) and Lark /agent purposes and the extensions' own purposes (`extension.<id>`, see "Extensions' own purposes"), plus `providers`; `GET /api/v1/model-config/purposes/{id}` returns one `purpose` and available `providers`, supporting legacy-purpose queries.

`Purpose` includes `id/name/group/kind`, `category_id`, `override`, `effective`, `revision`, `inherited_from/status`, `limit` when the connection is paused (see “Upstream rate limits”), and `fields/provider_ids` to constrain the form. The categories' `category_id` equals their own ID, with `uses: [{"name":"Read-only purpose description"}]`. The AI twin and Lark /agent point `category_id` to Agents but have their own `override`, `revision`, and nonempty `fields`; clients determine editability from `fields`, not solely `category_id`. Other legacy purposes point `category_id` to their owning category; `override` is empty, `fields` is `[]`, and revision and effective model come from the category. A task purpose (`task.<task id>`, requested by its own `GET`) points `category_id` and `parent` to Main chat but has its own `revision` and `override` and nonempty `fields` (provider, model, effort); with an empty override it follows Main chat, including later changes there. Real task names do not appear on the configuration home page. The `plugin.<plugin id>` model protocol remains independent and is not added to the four-category catalog. Responses contain no secrets.

Saving one item:

```json
{
  "revision": 0,
  "provider": "launcher.<provider name>",
  "model": "<specific model ID>",
  "effort": null,
  "runtime": "agentsdk"
}
```

Only `assistant` may write `runtime` (see “Main-chat runtime”).

“Information screening” (`inbox.triage`) also governs plugins: plugins using the Inbox without their own fallback require it to be callable before they can be enabled. With such plugins enabled, a change making it unusable returns 422 `triage_model_in_use`,
listing plugin names (clearing a selection still saves normally if fallback to `manager.json`'s `ai` / `inbox.triage_ai` or automatic selection remains callable; `docs/extensions/extensions.md`, “General rules for the Inbox”).

Send to `PUT /api/v1/model-config/purposes/{id}` or the compatible `PATCH` endpoint. The five category configurations, the AI twin, Lark /agent, the extensions' own purposes, and independent plugins are writable; other legacy purposes or task IDs return 400 (purpose models are read-only; edit the owning category). Missing fields are unchanged, `null` clears a selection, and nonempty values override. Success returns the same structure as a single-item GET. Only supported fields may be selected; a revision mismatch returns 409, and unknown purposes are not created ad hoc.
