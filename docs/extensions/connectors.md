# Connectors

A connector is Persona's standard way to connect a data source: GitHub, Messages (iMessage), Telegram, Lark and mail each have one. The hub's pipelines
(assistant tools, write gates, Inbox, knowledge base, status in Settings › Connectors, live events) attach automatically according to what the connector provides; adding a source does not require changing those pipelines.

This document has three parts:

- **I. Current structure (v1)**: the actual structure after the Lark and mail migration (M0–M6) and the merged GitHub, Messages and Telegram work. Follow this to add a connector.
- **II. v2 design**: eight comments on v1, each with agreement / disagreement, how to change it, size of the change, affected connectors and old/new compatibility.
  **Decided 2026-11-03** (results in part IV; the text already reflects them); V1 and V3–V6 are complete, V2 and V7 were rejected, and v2 is closed out.
- **III. Migration order**, **IV. Decisions**.

The process and history (why it was split this way, acceptance for each step) are in `docs/plans/plan-connectors.md`; Telegram is in `docs/archive/extensions/plan-telegram.md` (an extension since 2026-11-05, #1704; code in `nwverse/persona-extensions`, #2057).
Discord (the user's own bot, extension, #917): the first step (D1) is the `discord` extension; the later steps are planned in `docs/plans/plan-discord.md`.

### Interfaces: one manifest, dispatched by declaration

`server/internal/connector/connector.go`: `Connector` has `ID()`, `Name()`, `Manifest()`. The manifest (`manifest.go`, since v2 · V1) declares what it can do in one place:

| Manifest field | Meaning |
| --- | --- |
| `Capabilities` | Typed capabilities (`CapStatus`, `CapTools`, `CapActions`, `CapEvents`, `CapInbox`, `CapSettle`, `CapArchive`, `CapChats`, `CapItems`, `CapLogin`, `CapOptions`), each corresponding to an interface |
| `Hosts` | Link hostnames (for link recognition in the App) |
| `AgentTools` | Tools also given to Agents (not only the assistant), name globs (`mail_*` for mail) |
| `Unlisted` | Tools and writes excluded from the model's tool list, name globs: the connector's own frontend calls them by name (the Telegram extension's `tg` CLI and skill, `docs/protocol/connector-protocol.md` ("Command line")). Not a permission |
| `ConfirmAlways` | Writes that always require confirmation on the phone, name globs (optional): matching `allow` rules in `connector_gate` are clamped to `confirm`, while `deny` stays unchanged (see "Gate"). Written as `confirm_always` in extension manifests |
| `Poll` | How often to query `Archive` (0 is the hub default; mail is 6 minutes) |
| `Kinds` | Inbox item kinds; each needs a description in `prompts/inbox/kinds/<id>.md` (`connector.CheckKinds`, each connector's `TestKindsAreDescribed`); an undeclared kind received is logged |
| `Proxy` | Answers on behalf of another program (subprocess `proc.Conn`): implements every interface, but only declared ones are real |

The hub uses only `connector.As[interface](c)` to discover capabilities: it asserts the interface only when declared. `Registry.Add` checks the manifest with `connector.Check`: declared but unimplemented, implemented but undeclared (except `Proxy`),
unknown capabilities, or kinds without an Inbox capability all fail registration. Capability interfaces:

| Capability | Interface | What it does | Who has it |
| --- | --- | --- | --- |
| `status` | `Accounts` | `Status()`: state, accounts, a human-readable error sentence and `Guide` | All except Lark and mail (absence means `ok`; a `Proxy` is always asked for its own status) |
| `tools` / `actions` | `ReadTools` / `Actions` | Read-only tools; writes (`Describe` produces the card text and returns errors for bad parameters without showing a card; `Do` performs the write). A connector that knows the id of the message a write made also implements `RefActions` (`DoRef`: `Do`'s text and that id, for the sent-as-user ledger), and one that can take such a message back implements `Recaller` (`CanRecall`, `Recall`; "Sent as the user" below); one whose read tools can answer subscriptions with JSON implements `ReadJSON` (`CallJSON`; [subscriptions.md](subscriptions.md) "Existing connectors"); all three are found by type assertion, declare nothing and are optional (a program's connector, which implements every interface, is a `Recaller` only when it declares the capability `recall`) | See above |
| `options` | `Options` | Connector-specific settings (JSON), edited in the App | GitHub |
| `events` | `Events` | Live events, `changed(Scope)`; `Scope` is a typed constant, validated when received from subprocesses | Each has its own |
| `archive`, `chats`, `items` | `Archive`, `Chats`, `Items` | Three shapes for knowledge-base ingestion | See above |
| `inbox`, `settle` | `Inbox`, `InboxSettler` | Inbox candidates and replies (`Reply` receives the full `InboxReply`: conversation, item, which step it answers, body); settle old items by rule | GitHub, Messages, Telegram; `settle` only GitHub |
| `login` | `Login` | Stepwise login | Telegram, larkcli |
| `threads` | `Threads` | Opens an Inbox conversation as a chat page in the App: `Thread(thread, before, limit)` returns a page of messages (sender, avatar, media, references, cursor); `Media(ref)` supplies avatar/media bytes. Read-only; replies use the action named in `ThreadChat.Reply` (gated). The App selects a page by `ThreadChat.Kind`: bubbles for dm / group / channel, GitHub layout for pr / issue | Telegram (#1054), GitHub (#1055, `docs/plans/plan-connectors.md` ("Conversation page")) |

`Runner` (its own loop) and `Machines` (a computer connected) describe how it runs, not capabilities, and still use type assertions. Inbox tiers are `connector.Tier` (`TierAction`, `TierFYI`, `TierNoise`);
the hub drops unknown tiers and leaves classification to the model.

`Registry` (`registry.go`) owns all connectors: offers tools according to status (only `ok`), dispatches calls by prefix, enables/disables (`SetEnabled`), and starts `Run` / `Watch` (restarts with backoff after failure).

### Three execution models

- **In the hub**: Go code implements the interfaces directly.
- **Subprocess** (`connector/proc` ↔ `connector/serve`): first-party code whose dependencies are too large to compile into personad (Telegram's gotd; since #1704 Telegram is an extension using the process extension protocol). The hub starts the program; stdin / stdout carry the same
  JSON-lines RPC as hub↔node (`internal/rpc`), with methods corresponding to interfaces (`init`, `status`, `archive.changes`, `inbox.collect`, `tools.call`… in `wire.go`).
  The program calls the hub's `secrets.*` in the other direction. At registration the hub gives `proc.Conn` a static manifest (`proc.Config.Manifest`; extensions get it from their
  `persona-plugin.json`), so even connectors that have never started and are off by default can report capabilities and log in/out (#666). The program manifest returned by `init`
  (`serve.Manifest`, snake_case fields on the wire) is checked against it; mismatches are logged and the static one still wins. Marketplace extension programs are versioned independently of the hub; the protocol is versioned (v2, `docs/protocol/connector-protocol.md`).
- **node relay**: data exists only on a Mac (`chat.db`). A `Reader` on the node reads local data; the hub reads through node RPC (`connector.list/chats/older/changes/search`,
  five methods hardcoded in `node/node.go`; new nodes also answer through `plugin.node.call {id: "imessage"}`, see `docs/extensions/extensions.md` ("Built-in node programs"));
  the hub-side `imessage.Remote` is the connector. Choose the Mac in the built-in extension "Messages (iMessage)" (#1830 step 6); without a selection, use `imessage.machine` in the manager's manager.json.

  Messages identifies an entry by its canonical conversation and physical message ROWID. Multiple SMS/iMessage chat
  associations for that conversation count once in message pages, search results and unread counts; an association to
  another conversation remains a separate entry. A changes page's limit counts distinct physical messages, so a message
  belonging to several conversations may produce more entries than that limit. The page selects its boundary and expands
  all its chat associations in one SQLite snapshot; `more` counts distinct messages and the numeric `next` cursor advances
  only after the last selected ROWID's associations are processed, including conversations filtered out by the keep rule.
  History reads reject a conversation with more than 200 associated chats; changes and search reject a read that exceeds
  10,000 or 40,000 expanded associations respectively. Failed reads return no page cursor. Search considers at most
  20,000 distinct physical messages before applying its result limit. Existing numeric cursors remain valid, but a cursor
  already advanced by an older version cannot recover an association that version skipped; no stored state is reset.
  Message history keeps its existing join-date order and message-date cursor semantics.

### Gate

- The gate handles only **AI-initiated** writes (assistant tools, `tg` CLI / skill, Agents, all through the node's `mcp.call`): `Registry.Call` →
  rules in `connector/gate.go` (`connector_gate` in the manager's manager.json, first match wins) →
  `allow` runs directly, `deny` refuses, `confirm` (default) shows a card on the phone (`hub.approve`, expires in 15 minutes). The card says what will happen, the full text, and who will see it.
  For writes matching the manifest's `ConfirmAlways`, even `allow` rules (including `*`) are clamped to `confirm` (`Decide`), while a `deny` that matches stays unchanged; the manifest registered by the hub wins, and a program's self-report cannot loosen it.
  A call whose arguments give a field more than once is refused before any rule is read (`repeatedField` in `connector/gate.go`, error kind `declined`): the very same name, or names that differ only in capitals by `encoding/json`'s case folding, among the top-level fields. The message names the field and tells the model to write each field once, spelled as the tool defines it. A connector that decodes its arguments into a struct reads such a call by rules the gate's map does not follow (it takes the last value in the plain case, but ignores a `null` and decodes an object or an array onto what the earlier one left), so a rule cannot tell which value the write would use, and an extension in another language may read the names some other way again; the gate does not guess, for any connector.
  A `deny` or `confirm` with a `match` reads field names without regard to capitals, the rule's own as well as the call's (`matchFieldsAny`), so a call that spells a field once in other capitals is refused or asked as if it were spelled right; this refuses or asks for more calls than before. An `allow` reads the exact names, so such a call does not hit it and goes on to the later rules, ending at the default `confirm`. Arguments that give each field once, spelled exactly, are decided as ever. Ignoring the case of a name is what the built-in connectors do, and extensions written in Go with `encoding/json`. The node's Feishu gate does none of this: it compares a request body by exact field names (`bodyMatches` in `node/larkgate_rules.go`, also for the rules `connector.GateRules` gives it), and the service that gets the body is not one this repository decodes.
- **Manual actions by the user bypass the gate** (#1190, user: "Why do I need to approve a message I send myself? That's completely wrong"): replies from the conversation-page composer
  (`POST …/thread/reply`) sent by the user's own logged-in device (phone, Mac, web full device token) use `Registry.Run` directly, without a card;
  `deny` rules do not block them either. Identity comes from hub authentication (`byOwnDevice` in `extmgr/helpers.go`), not client-reported fields; hub.json pairing tokens, pairing codes,
  machine / linked-hub credentials are not devices and still go through the gate. Lark sends and Inbox "Send" already bypassed it. Taking back what was sent is the same kind of act, and gets the same rule: the user's own device asks once in its own dialog and the route runs it with no card (**Recall**, below).
- Lark writes are not tools: the assistant uses commands / lark-cli in the Lark extension's skill; the node's Bash hook (`node/larkgate.go`) reads the command to distinguish reads and writes. Its rules are
  `connector:"lark"` in `connector_gate` (`action` is "method path"), plus the old `lark_gate` and built-in rules (M5).
- Tapping "Send" in the Inbox is itself confirmation, so `Reply` shows no extra card; the conversation-page composer works the same way (above).

### Sent as the user

Every write that went out through the gate is kept in the ledger `sent_as_user` (migration `manager/0420`, #5278), so the user can see what Persona wrote in their name, where, and why it was allowed. The ledger is on the manager's side: the gate runs there, and so do the approval card and the conversation that asked.

- **What is a row**: a gated call (`Registry.Call`) whose action (`Do`) returned without an error; `Registry.SetSent` tells the manager (`recordSent` in `extmgr/sent_ledger.go`). Not a row: a write the gate denied, one the user declined on the phone, one whose `Do` failed (a program's `Do` that timed out may have happened anyway; nothing is kept for it), and everything the user sent by their own hand (`Registry.Run`: the conversation-page composer, Inbox "Send", Lark sends). Taking a row's message back is described below (**Recall**). An extension's connector that sends in the user's name by itself, outside the gate, and says so in its manifest (`contributes.connectors[].sends_as_user`), can put such a send in the ledger with `sent.record` (below). The assistant's Lark writes through the node's gate proxy come in with `lark.sent` (below).
- **Archive provenance** (#2814): extensions granted both `kb.read` and `sent.read` can read `kb.day` origin marks (`sent_by`, `sent_ledger_id`, and `recalled_at` for recalled sends). Only unique matches are marked; recall preserves authorship, and an unmarked line is not proof the user typed it. This reads the existing ledger without changing sending or confirmation. Matching rules, permission status, and known gaps are in [Knowledge base RPC](extensions.md#knowledge-base-rpc-1908).
- **Columns**: `id`, `at`, `connector`, `action`, `target` (where it went), `text` (what it said, at most 4000 characters), `summary` (one line), `origin`, `let_through`, `message_ref`, `recalled_at`.
  - `target` is read from the arguments: GitHub comments and reviews `{ref: "owner/name#12"}` (a review also `event`); mail `{to, cc?, bcc?, subject, account_id?}`; any other connector (an extension's too) the fields they usually name a destination by (`chat`, `thread`, `channel`, `conversation`, `recipient`, `to`, `reply_to`, `subject`, `repo`, `number`), and when none is there `{arg_keys: [...]}`, the names of the arguments it was given.
  - `summary` is the first line of the card's words when the user was asked, else the action and its target; for an extension's own record the line it gave, else `<connector>: <target fields>`.
  - `origin` is the conversation that asked, `{machine_id, session_id}`; `{}` when the request named none (a pairing token's reply in a connector's thread). For a send an extension recorded it is `{extension: <id>}`, with `machine_id` and `session_id` beside it when the extension named them. For a Lark write through the node's gate it is `{machine_id}` (the computer the write ran on) with `session_id` when the node knew the conversation.
  - `let_through` says how the gate let it through: `{kind: "rule", rule: {connector, action, match?, decision}}` for the `connector_gate` rule that allowed it (`user_rule: true` beside `rule` when it was one the user made from the ledger, "Per-chat rules" below, not one written in manager.json: the kind stays `rule`, so a client that does not know the mark shows "by a rule" as before), or `{kind: "card", interaction_id, answered_by?}` for the phone card (`answered_by` is `assistant` when the assistant answered it for the user, absent when the user did). A rule's `allow` that `confirm_always` or a health conversation clamped to a card is a card. A call refused for giving a field more than once writes nothing and has no row. An extension's own record is `{kind: "auto", setting?}`: no rule and no card, `setting` being the extension setting that let it send without asking. The node's Lark gate also accepts `{kind: "permission_mode"}` for classified ordinary writes allowed by assistant bypass (no phone answer), and `{kind: "conversation_always"}`: the user had chosen "Always allow in this session" for that route, so no card was shown.
  - `message_ref` (the sent message's id on the other side, kept as the service wrote it, only trimmed and with no NUL; one longer than 200 characters is not cut, because a cut id points at nothing or at another message, but left empty, the same for all three sources of a row: `proto.CleanMessageRef`) is what the write said it made, empty when it did not say. `recalled_at` is written by a recall (below). Per source: a connector with `RefActions` says it through `DoRef` (`Registry.call` asks it instead of `Do`); GitHub's comment is the new comment's `id` (`github_comment`) and its review the review's `id` (`github_review`), in decimal (an id that is not a positive whole number leaves it empty and never fails the post: it is read after the post went out): they are different resources with numberings of their own, so the id alone does not say which and the row's `action` and `target.ref` (`owner/name#12`) are what a recall goes by; mail is the Message-ID written into the header of the message that went out, without the angle brackets (the form of `message_id` in the mail API's message lists; whether a provider keeps it as written has not been checked); an extension's connector answers it in `actions.do`'s `message_ref` (`docs/protocol/connector-protocol.md`), an older one answers none and the row is written all the same; the node's Lark gate reads it from the API's answer (below). A connector that does not say leaves it empty, and so does a recorded send (`sent.record`) that gave none.
- **Sends an extension made itself** (`sent.record`, #5278 step 2): a gate sees only the writes that pass it, and an extension's connector can also send from inside a tool that reads. Such a connector declares `sends_as_user: true` in its manifest (shown at install as "Send messages as you", and asked again when an upgrade adds it), and its program calls `sent.record` after each send (`docs/extensions/extensions.md` "Sent as the user: `sent.record`"). The hub (`extensionSentRecord` in `extmgr/sent_ledger.go`) accepts it only from a connector of the caller's own that declares the field (else `permission_denied`; the user switching that connector off afterwards does not matter, the send happened), forces `origin` to the extension (its `machine_id` and `session_id` are the extension's own word) and `let_through` to `auto`, cuts the text to 4000 characters like a gated write's, keeps the target's short values and limits each extension to 60 calls at once and then one a second. The ledger is then as complete as the extension is honest: the hub does not see the sends it is not told of, and the install line says so.
- **The assistant's Lark writes** (`lark.sent`, #5278 step 3): the node's Lark gate (`node/larkgate.go`) decides before the command runs and cannot see whether it sent. A gated command whose gate has `auth` goes through the node's gate proxy (`node/gateproxy.go`), which sees the status the API answered with. For every write it forwarded (any method but GET and HEAD) that came back 2xx (201 and 204 as much as 200), the proxy tells the manager with a `lark.sent` request once the answer has gone to the command, also when it could not finish passing on the answer's body (the API had taken the write by its 2xx). The report does not wait for the manager: it runs in the background, at most 32 at a time (one over waits up to a second for a place, then is logged and not told), and one that fails is only logged on the node. Reads, requests the proxy refused, redirects, 304 and failures are not told, and neither is a command that went away before the API answered (whether the API ran it is not known). The manager (`RecordNodeSent` in `extmgr/sent_ledger.go`) takes it only from a computer it knows, and the row's `origin.machine_id` is the connection's, whatever the request says. The row is `connector: "lark"`, `action: "<METHOD> <path>"` (the way `connector_gate` writes a Lark rule), `target: {command, method, path}` (`command` is the gated command, the gate's own name) plus `conversation` and `message` when the path names them REST-style (`/conversations/<id>/…`, `/messages/<id>/…`; a path that names a collection twice or has no id after it gives none), `text` the body's `body`, `text`, `message`, `content` or `comment` field (the first with words, a JSON body only) cut to 4000 characters, and `let_through` as above. The conversation comes from the card or the process: the session `larkCheck` decided for when the write was confirmed or covered by "Always allow", else the one the assistant's process was started for (a write a rule allows). A grant a confirmed write is let through by belongs to the conversation it was confirmed for: another conversation's identical call does not use it up. When the manager answers the node's card from an "Always allow" it kept (after the node restarted, or because a card answered meanwhile covers it) it says so (`remembered: true` on the resolution), and the row is `conversation_always`, not a card that was never shown (an older manager does not say so and the row is a `card`). What the ledger does not have: writes through lark-cli (it carries its own credentials and does not pass the proxy), gates without `auth` (their credentials are in the command's environment, so the node never sees the answer), a write the node could not tell the manager of (the manager was not reachable, or the node had no hub connection), and a write the API answered 2xx but whose body says it failed (the proxy reads the status, and the id described next, only).
  - *The message id* (`message_ref`): the proxy keeps a copy of the first 256 KiB of a 2xx JSON answer to a write while it passes the answer on (the command gets the bytes, headers and status as the API sent them, flushed as they come: the copy is made after each write, it is not a buffer in front of it), and the report reads the id from the copy once the answer has gone: the first non-empty string among `data.message_id`, `data.messageId`, `message_id` and `messageId` (a gateway's receipt names it one way, the Open Platform's answer another), as the API wrote it (one longer than 200 characters is none, not cut). gzip answers are read, whether the command asked for gzip (the answer passes compressed and the copy is unpacked) or not (the proxy's transport unpacks it first). No id, not JSON by its Content-Type, cut off, longer than the copy (256 KiB, also once unpacked), compressed some other way: the write is reported all the same, with no id. Only the id leaves the node; the answer is never logged. The manager keeps it only for a route that creates one message in a conversation the path names: `POST /conversations/<id>/messages` and the attachments' routes (`/conversations/<id>/images`, `/files`, `/attachments`, `docs/extensions/lark-attachments.md`, `docs/extensions/extension-messaging.md` "6"). **Known limit**: a reply (`POST /messages/<id>/replies`) and a forward are not known to answer with the new message's id, and a reaction or a read position answers with the id of a message that is someone else's, so their rows leave `message_ref` empty for now: a wrong ref (the one a recall would act on) is worse than none. A route is added when its answer is known to name the message it made. An older node does not send the field and an older manager ignores it.
- **Recall** (#5278: the core and the route; the button on the web and Android, #3100, and on iOS and the Mac, #3219): a connector that can take back a message one of its writes made also implements `connector.Recaller`, next to `RefActions` (found with `connector.RecallerOf`; a built-in connector declares nothing and `Check` does not look for it, a program's connector is one only when its manifest declares the capability `recall`, which has no interface to check: see **Extensions** below). `CanRecall(action, age)` answers from memory whether the message that action made, `age` ago, can still be taken back (the limit a service sets on how late is the connector's own); `Recall(ctx, SentMessage{Action, Ref, Target, At})` does it, with the row's action, `message_ref`, `target` and `At` (when the row was written, which a connector with a limit of its own counts from). It returns nil only when the other side confirms the message is gone (one that was already gone included, and a repeat after success succeeds too), an error wrapping `ErrRecallUnknown` when the request may have taken effect (a timeout, a lost connection), one wrapping `ErrCannotRecall` or `ErrRecallUnavailable` when nothing was sent (the row names nothing the connector could have written, or it is a kind it cannot recall; no token, offline, the token refused), and any other error when nothing changed (the other side refused, or whether the message is gone could not be checked).
  - **GitHub**: `github_comment` is taken back by deleting the comment (`DELETE /repos/{owner}/{repo}/issues/comments/{id}`, the id being the row's `message_ref` and the repository the one in `target.ref`; the same write permission as posting it). Only a 204 is a success: a repository that moved answers 301 and the client sends the request on as a GET, which answers 200 and deletes nothing, so a repository renamed or transferred since the write cannot be recalled (the outcome is unknown; a 307 or 308 would keep the DELETE, but GitHub documents 301). A 404 is looked into, because GitHub answers it for a comment that is not there, for one the token can read but may not delete (a public repository) and for a repository the token cannot see: the connector reads the comment itself. It can be read: it is still there and the delete was refused (`recall_refused`). It cannot be read (404) and the issue it was on can (or was deleted, a 410, which takes its comments): the comment is gone, which is what was asked for, and a repeat after a lost answer succeeds too. Anything else (a lookup that fails, an issue that cannot be read) leaves nothing known and is a refusal, not an unknown outcome, as the 404 deleted nothing. `github_review` cannot be taken back: GitHub deletes only a review that was never submitted ("Submitted reviews cannot be deleted"), and dismissing one leaves it on the page. **Mail** cannot be taken back, and neither can what an extension's connector did not declare `recall` for (a program's connector, `connector/proc`, is a `Recaller` only then: see **Extensions** below).
  - **`RecallSent`** (`extmgr/sent_recall.go`) is what the route calls with a row id and `confirm`, how the caller made sure the user agrees: it runs after the checks and before the connector, and an error from it stops the recall, so a card or the user's own device can be passed without changing the core (a `nil` confirm refuses to run). Nothing in it says who may ask: the caller applies the ledger's read rule (below) and refuses what an extension or a conversation started. Two recalls of one row at once each call `confirm` (and the connector), so the caller dedupes them (the route does, below). The checks (`recallCheck`, which a page of the ledger can use to say which rows offer a recall): not taken back already, the connector is registered, is a `Recaller` and `CanRecall`s the action, the row has a `message_ref`, the message is not older than `sent_recall_hours` (manager.json: 24 hours when omitted or 0, no limit below 0) nor than the connector allows (the stricter of the two, judged when the request comes), and the connector is available (switched on, signed in). Only when `Recall` says the message is gone is `recalled_at` set, once (`UPDATE … WHERE recalled_at IS NULL`), also when the request went away meanwhile; a refusal and an outcome nobody can tell leave the row as it was and can be asked again. Two recalls at once both reach the connector (which allows repeats), but only the first marks the row; the other gets `already_recalled`. The connector has `sentRecallTimeout` (30 seconds) for its recall, and what it says decides the code: an error wrapping `connector.ErrRecallUnknown`, or one that came when the time ran out or the request went away, is `recall_unknown`; `ErrCannotRecall` (it found it could not, before it sent anything) is `not_recallable`; `ErrRecallUnavailable` (no token, offline, the token refused) is `connector_unavailable`; any other error (the other side refused, or whether the message is gone could not be checked) is `recall_refused`.
  - **Failures** are a `*RecallError{Code, Err}`; the route answers by code, with these statuses: `not_found` (no such row, 404), `not_recallable` (no `Recaller`, no ref, not that kind of message, or the connector found it could not before it sent anything, 409), `too_old` (409), `already_recalled` (409, with the row), `connector_unavailable` (switched off, not signed in, offline, its token refused, 503), `recall_refused` (the recall did not happen: the other side refused, or whether the message is gone could not be checked; nothing was changed, 502), `recall_unknown` (it may or may not be gone, nothing recorded, safe to ask again, 504) and `no_database` (503). A database that fails, or a mark that fails after the message was taken back (asking again finds it gone and marks it), is a plain error for a 500. The route adds its own: 403 `own_device_only`, 400 `confirm_required`, and 400 for an id that is not a number from 1.
  - **The route** (`POST /api/v1/connectors/sent/{id}/recall`, `extmgr/sent_recall_route.go`; `docs/protocol/protocol.md` "Connector API"): `{"confirm": true}` runs `RecallSent` and answers `{ok, item}` with the row as the ledger now has it.
    - *Who*: only the user's own full devices, by hand (`byUsersOwnHand`: `byOwnDevice` and no extension, as the hub's authentication finds them, not a field the client sends). Not the owner's master token on the hub machine, although that reads the ledger (`mayReadLedger`): any process on that machine can read the token, and in the audit what it did cannot be told from a person's. This is the line #1190 drew for what needs no card: the conversation-page reply route is `byOwnDevice` as well (`extmgr/connector_threads.go`), and so are the browser sign-ins (`extmgr/browser_cookies.go`). An answer-only device, a pairing token and an extension's token are refused too. A refused request is 403 `own_device_only`, and the answer says why. The hub does not open the route to an extension's token at any scope (`-` in `hub/testdata/route_scopes.txt`), and the handler refuses one that got through.
    - *The user's agreement is the request*: the app asks once in its own dialog and sends `confirm: true`, and the route then recalls with no card shown on the phone. This follows #1190: a message the user takes back with their own hand on their own device is not asked about a second time, as the reply they typed there is not; cards are for what the assistant does. The field is there so that a stray POST (an empty body, a retry by something in between) cannot delete a message: without it the answer is 400 `confirm_required` at once, the connector is not asked, and the request does not take a place behind a recall on its way.
    - *The assistant* has no recall tool and holds no hub credential of its own: the assistant talks to the hub over its bus, and a chat's processes reach the connectors' tools through the node, with no hub token. The owner's token is refused here. Whatever holds the owner's token on the hub machine is trusted as the user anyway (it may add devices), so against it this route is no stronger than the composer's own replies (#1190); what it adds is that a recall is made from a device, which the user sees in their devices and in the audit. A recall the assistant starts is not this route's: if one is added, it is an ordinary write, a connector action through `Registry.Call` and its gate, with the card.
    - *Audit*: a recall that took the message back is recorded in `plugin_audit` like a sign-in or a switch (`connector_recall`, with the connector's id in the `plugin` column, `{row, action}` as the detail and the device (`device:<id>`) as the actor; never the message's text). What took nothing back (a refusal by the route or the connector, a recall nobody could tell the outcome of, one already taken back) records nothing: the row is as it was, and the core logs the failure. A record that cannot be written does not undo the recall.
    - *Several requests for one row at once* (`recallLocks`, per row): the first confirmed request calls the connector. Every request that joins while it is on its way waits for and receives the same row and error, never calling the connector itself. A shared success is 200 `{ok, item}` for every caller, with the same `recalled_at`; a shared failure keeps its real status and code, including 504 `recall_unknown` (never success and never a generic busy answer). Only the caller that ran a successful flight writes the audit record. A request after the flight is a new user attempt: if the row was taken back it gets 409 `already_recalled`; after refusal or unknown it may try again. A waiting request stops when its own client goes away without cancelling the shared recall, and a recall of another row is not held up. Nobody waits for more than one recall: at worst the connector's `sentRecallTimeout` (30 seconds) and the mark (10 seconds), about 40 seconds. That is inside what the hub allows: the relay from the hub to the manager has no limit on a response except five minutes for it to begin (`ResponseHeaderTimeout` in `hub/extensions_link.go`), and neither server has a write timeout. **For the button's request**: an app's own request timeout is the app's, and the defaults are too short for this one, so allow at least 60 seconds: iOS's `APIClient` defaults to 30 seconds (pass a longer `timeout`), Android's hub client reads for 15 seconds by default (pass `readTimeoutSeconds`, as `HubSessionFiles` does with 100).
  - **What a row says about it** (`extmgr/sent_recall_rows.go`): each row of `GET /api/v1/connectors/sent` and the `item` the route answers with have `can_recall`: the answer of `recallCheck` at the moment of the read, the one `RecallSent` acts on. There is no `recall_until`: a screen shows the button by `can_recall`, and a message that ages out before the tap is refused with 409 `too_old`, which the screen answers by reading the ledger again; if a countdown is ever wanted, `Recaller` gets a method that says the window (`CanRecall` says only whether an age is allowed). The field is extra: a client that does not know it reads the row as before (the web, iOS and Android readers each take the fields they know). A connector that is switched off or signed out has `can_recall` false for the time it is, and so has GitHub while it is rate limited (the same `connector_unavailable` a recall would answer).
  - **Extensions** (#5278): a program's connector that can take back what it sent declares the capability `recall` in `contributes.connectors[].capabilities` (no new manifest field: an older hub drops a capability it does not know and runs the connector without it). `connector/proc.Conn` is then a `Recaller`: `CanRecall` answers from the manifest (any action; the hub's `sent_recall_hours` is the only time limit it can know, the program's own is its to judge), and `Recall` first gives a current program the read-only `recall.can` preflight and then `recall.do` (`docs/protocol/connector-protocol.md`) with a stable opaque `request_id`, the row's action, `message_ref`, target and time, once `RecallSent` has the user's yes. An older program that has no `recall.can` receives only legacy `connector.recall`; a program that answers `can` but lacks `do` is not sent a second kind of write. Only `done` and `already_recalled` are success (`recalled:true` on the legacy path); `not_recallable` becomes `ErrCannotRecall`, `unavailable` becomes `ErrRecallUnavailable`, `unknown`, an empty or unrecognized status, a dropped connection, a deadline or a malformed answer becomes `ErrRecallUnknown`, and `refused` stays the service's plain refusal. One request id shares an in-flight program call and replays confirmed success; failed and unknown outcomes remain explicitly retryable. The program receives no message text, origin, approval record, account or credential. The row is asked of the one extension that provides `row.connector` now (connector ids are unique), never of another. It is shown at install ("Take back messages it sent in your name", from `extension.ExplainWith`) and, unlike `sends_as_user`, is not in the digest the user agrees to, nor in what an upgrade adds (`AddedIn`, `MorePermissions`): a recall happens only after the user asked for it, so it gives the program nothing to start by itself.     - **A write the node's gate proxy reported** (`lark.sent`) is a row of connector `lark` whatever gate it went through, and names no extension, only the gate: `target.command`, which every such row has (the node writes the gated command it forwarded for, since the report's first version). The hub asks the extension that provides `lark` only if that command is one of the extension's own gates (`contributes.assistant[].gate`'s `command`, read from the gate file when the extension starts) **and no other extension has a gate of the same command**. A command is checked for its format only, so two extensions can have one, and the node then uses one of them: whose the write was cannot be told, so neither is asked, and an extension with no program counts. Only the extensions the assistant is given the gates of are counted (`assistantGates`: enabled, with no problem; one that still needs setting up counts, a disabled one or one that cannot run on this hub does not), and only those the hub has applied (`extensions.apply`): one not applied yet, as at hub start, is not counted, so this guards a row from the moment every extension is up. A gate row of a connector that no extension provides (a built-in one) is `not_recallable` too, whatever gate it names. The extension may check the command again. A write through an extension's own connector (`actions.do`, `sent.record`) names its connector and is not held to this.

A row written while two extensions had one command is asked of the one that still has it once the other is removed, and a row written through another extension's gate is asked of the extension that provides `lark` if an upgrade of that extension adds the command (the install time below is the extension's, not the gate's). A gate renamed by an upgrade leaves its old rows `not_recallable`. The per-chat rule of such a row is unaffected: it goes by the commands of the gate files with `connector: "lark"` and does not ask whose the write was, so a row whose gate two extensions share can still get a rule and is not offered a recall.
    - **A send before this install** is not asked about: the extension's `InstalledAt` (an installed extension only: it is when it was first installed, an upgrade, a configuration change, switching it off and on, a rollback and a restart keep it, uninstalling and installing again does not) is `hubExtension.recallNotBefore`, checked in `recallOwnerCheck` and again by `proc.Config.RecallNotBefore` when the program is asked, so what the ledger wrote for an extension since uninstalled is not sent to another that took its connector's id. A dev extension and a built-in one have no such limit. Known limit: it is the extension's time, not the connector id's, so a connector id that an upgrade adds to an extension counts from the extension's first install, not from the upgrade: what another extension, since uninstalled, wrote under that id in between is asked about. What was sent before uninstalling and installing the same extension again cannot be taken back.

The connector provides `InboxThing` (one thing: `Thread` is its key, `Kind` its own kind, `Tier` / `Why` the tier chosen by its rules, and `Done` means it observed completion);
each round, the hub hands candidates to the manager (`inbox.collected` on the bus, `docs/assistant/inbox.md` ("Who owns what")). The manager (`applyConnector` in `assistant/inbox_connectors.go`)
merges subsequent activity for the same `Thread` into an open item. Classification, AI twin, completion and retention then belong to the manager and are the same for every source; replies, `Settle` and tools derived from events
are still dispatched to connectors by the hub (the manager asks through `app.call inbox.*`). Items use a generic block (`InboxConnector`), so the App can render them without knowing the source.

The built-in `larkcli` connector keeps its cursor, bounded message-id overlap set and topic-participation set in the manager's Postgres settings store. Its `inbox.collect` implementation only returns the connector's in-memory round; the subprocess is called by the connector watcher, which emits `changed {scope: inbox}` after a round with a new item. A two-minute poll is the default (configurable under `lark.cli`, never below one minute), and no lark-cli Inbox read runs while an available Lark gateway is the preferred source.

**Maintainer opt-in addition (separate from L4):** `larkcli` exposes the connector option `inbox_all_chats`, a list of chat ids. When the list is non-empty, every new message from those chats is collected in addition to the L4 rules (the user's own messages are still dropped). It is off by default and can be removed independently if broad chat collection proves too noisy.

### Knowledge-base ingestion

- `Archive`: one cursor per account; `Changes(cursor)` returns changed conversations. The hub stores the cursor in `cursors/<id>.json`; conversation ids are `<connector id>-<conversation id>`.
- **What the knowledge base's selection reads** (#1523): the selection decides which chats and documents are kept by
  what the connector reports, so every connector that reports it behaves the same. A batch's chat (`kbwire.SourceChat`)
  has a kind (the kind rules match dm / group / bot / official / system; other kinds such as mail, issue or pr match
  none) and the owner's flags `muted`, `collapsed` and `done`; a message has `mine`, `mentioned` (the owner by name: the
  connector decides what counts) and `mentioned_all` (an @all / @everyone, reported apart so the selection's
  `include_all` can decide), on `Changes` batches as on history pages; a document (`kbwire.Item`) has `signals`, the ones it can tell of `mentions`,
  `comment_mentions`, `authored` and `viewed`. All of them are optional: a connector that cannot tell one leaves it out,
  and its chats or documents never match that rule (a document with no signals at all is kept as before the selection).
  Per-item settings are keyed by the stable chat id `HistoryChats`
  lists (`GET /api/v1/kb/selection/candidates` shows that list), or by a document's item id, and the history import reads what the selection says,
  so a connector has nothing of its own to decide about which chats are imported.
- `Chats`: for sources like Lark with per-conversation cursors and attachments, provide `kb.Source` directly; archiving, compression and tagging stay unchanged. Older history is imported separately (`docs/assistant/knowledge.md`, "History import").
- `History` (capability `history`, requires `archive`): a conversation's older history, which `Changes` never reaches.
  `HistoryChats` lists the conversations that can be imported (kind dm / group / bot / official / system, the
  `muted` / `collapsed` / `done` flags, a rough message count; a conversation id is unique across the connector's archive sources, since a query names it by
  id alone); `History` reads one page of one conversation (before / after / around a position, or the
  newest page). Optional `HistoryAnchors` (capability `history_anchors`) searches for the messages the owner sent or
  was mentioned in, so a conversation can be imported as windows around them (each anchor says the source its
  conversation is filed under, since one the account left is often missing from `HistoryChats`). All read-only. The knowledge base drives
  the import through the hub's bus methods `connectors.history_chats`, `connectors.history` and
  `connectors.history_anchors` (`assistantwire/kb.go`); extmgr routes them only to a connector that archives into the
  knowledge base now and declares the capability, checks the query and cuts its limit to 200, and passes the answer and
  any error back as they are. `connectors.archives` says which connectors have them (`history`, `history_anchors`).
  What the caller relies on (`docs/protocol/connector-protocol.md` "History"): a page's limit is a hint and a source may
  answer more, so the caller goes on from the cursors it answers; `more` false or an empty page is the start of the
  conversation, unless the answer is paced or unreadable (`HistoryPage.AtStart`); a conversation the account can no longer read is `unreadable` (skip it, not a failure); `pace` asks the
  caller to wait (`retry_after_ms`) or stop for a person (`stop`, `reason`); a read that timed out is never retried by
  the caller.
- `Items`: Lark documents, meetings and calendar events.

### Settings › Connectors

`GET /api/v1/connectors?all=1` (without `all`, omits Lark and mail for pre-M6 Apps); each entry is `{id, name, status, account, via, error, guide, guide_url?, missing_scopes?, capabilities, hosts, enabled, options, archive, inbox}`. `guide_url` is an optional HTTPS page the App may open for a connector-specific fix; `missing_scopes` names permissions when available.
`archive` / `inbox` are the "Add to knowledge base" / "Add to Inbox" toggles (`Registry.SetFeed`, on by default, stored in hub settings). Turning knowledge-base ingestion off stops new content from its conversations, documents, meetings, calendar events and posts: the connector is omitted from both knowledge-base source lists, calls to `Archive`, `Items` and document-title lookup are refused, and the program's `kb.posts_*` calls are refused too. Content already saved stays. The connector keeps running and tools remain available. Turning the connector's main `enabled` switch off also blocks these knowledge-base paths, even if its extension process remains running for another capability.
"Delete stored knowledge-base content" (`DELETE …/{id}/archive`) turns knowledge-base ingestion off and deletes the connector's conversations and people, including its `archive_sources`, archived posts, and documents, meetings and events. It also removes their indexes and project associations and resets archive cursors and deleted chats' history-import state. The connector keeps running; Inbox entries and tools stay available.
"Delete stored data" (`DELETE …/{id}/data`) performs the same knowledge-base cleanup, disables the connector itself, and deletes its Inbox entries. Both responses include `chats`, `people`, `posts`, `items` and `inbox` counts (`inbox` is zero for knowledge-base-only deletion). Deletion does not sign out or change data at the remote service.
Ownership is recorded when data enters the knowledge base. Older records without ownership are deleted only when their source or source chat identifies this connector; ambiguous records are retained to protect other sources. See `docs/assistant/knowledge.md` ("Deleting a connector's saved knowledge") for the legacy and shared-source rules. Disabling Inbox ingestion stops `Collect` without changing existing inbox items.
The App draws the whole section from this list: Lark and mail retain their original rows (status still comes from their own APIs), Messages has its own page, and others use the generic connector page. On web Settings › Connectors, the `larkcli` status lives in the Lark bot group. API details in `docs/protocol/protocol.md` ("Connector API").

Audit: signing in or out, the switch, the two feeds, the connector's own settings, deleting its data or knowledge base content and GitHub's token source are recorded in `plugin_audit`
with who did it (#5281); never a credential or a typed value. The actions and their details are listed in `docs/extensions/extensions.md` (after the install / upgrade steps).

### Adding a connector (v1 approach)

1. Create a `connector/<id>` package implementing `Connector` (including `Manifest()`) and its declared capabilities; tool descriptions go in `prompts/mcp/<id>/`, Inbox kind descriptions in
   `prompts/inbox/kinds/<id>.md`; declare kinds in the manifest and add `TestKindsAreDescribed`.
2. Add a config section to the manager's manager.json (`docs/operations/config.md` ("manager.json")) and register it in `registerConnectors` in `extmgr/connectors.go`.
3. Writes must be `Actions`; the `Describe` card must say who will see the result.
4. `Status` answers only from memory (queried on every tool listing); errors get a one-sentence `Error`, and self-service fixes get a `Guide`.
5. No body text, phone numbers or tokens in logs/errors.
6. For external services, embed `connector.Egress` (`connector/egress.go`) in config to get a `proxy` key (`http://[username:password@]host:port`, empty means direct).
   Build every HTTP client with `Egress.HTTPClient`: use the proxy when configured, direct otherwise; invalid config errors rather than silently connecting directly. This is how `github.proxy` works (#1106);
   proxy-address parsing lives in `netproxy`, also used by `google.proxy`. Not yet wired: Telegram (MTProto, not HTTP), subprocess / third-party connectors (proxy must be passed to the program), see #1106.

> **Process-extension connectors live outside the hub**: for example, a personal WeChat connector is a client for an external API service, delivered as an extension package (`.tar.gz` plus sha256) and installed from the extension marketplace.
> It speaks extension protocol 1 and connector protocol v2 to the hub and declares `fallback` (each Inbox item carries a fallback tier). Its code is outside this repo; the extension and its integration guide are published from its own repository.
> This repo retains only the wire fixtures and manifest for the neutral `examplechat` ("Example chat") connector (`schema/extension/examples/Manifest.examplechat.json`).
> Conformance testing for such external programs: use `conformance.Program` for extension-side start/stop and handshake ([extensions.md](extensions.md) ("Conformance tests")),
> and `CheckProgram` with synthetic wire fixtures for connector-side capability checks ([connector-protocol.md](../protocol/connector-protocol.md) ("Conformance tests")).

## II. v2 design

The assessment of v1 was "usable, well documented, but not elegant enough". Below are judgments on eight points after reading the code. Change sizes are estimated as "small: one or two PRs, hundreds of lines, no App changes",
"medium: three to five PRs, possibly App changes", "large: crosses hub / node / programs / App, needs several steps".

### 1. Capability declarations: one explicit manifest

**Agreed.**

Current state: 19 optional capability interfaces (`Accounts`, `ReadTools`, `Actions`, `Options`, `AgentTools`, `Validator`, `Events`, `Runner`, `Machines`, `Hosts`,
`Poller`, `Chats`, `Items`, `Archive`, `Inbox`, `InboxReplier`, `InboxSettler`, `Login`, `Capabler`). The problem is not just their number:

- Two declaration systems. In-hub connectors use "which interface is implemented", subprocesses self-report through `Capabler`; to represent any program, `proc.Conn` implements every method it can forward over RPC,
  so the hub's assertions always succeed, and correctness depends on the program "returning empty if unsupported". `Capabilities()` (then in `connector/registry.go`, now `Capabilities` in `connector/manifest.go`) reports only 11,
  leaving `AgentTools`, `Validator`, `Poller`, `InboxReplier`, `InboxSettler` invisible in `GET /api/v1/connectors`.
- Some entries are data, not behavior: `Hosts`, `AgentTools`, `Poller` each returns an unchanging value (constant or config).

Proposal:

```go
type Connector interface {
    Manifest() Manifest // Read once at startup; subprocess reports the same structure in its handshake
}

type Manifest struct {
    ID, Name     string
    Protocol     int          // Connector protocol version (point 4)
    Capabilities []Capability // Typed constants: CapStatus, CapTools, CapInbox, CapChanges, CapLogin, CapOptions…
    Hosts        []string
    Tools        []ToolSpec   // Each tool: name, read/write, exposed to Agents (replaces AgentTools, per-tool granularity)
    Inbox        *InboxSpec   // Kinds (name, label, default tier), reply support, whether it settles old items itself
    Changes      *ChangesSpec // Poll interval (replaces Poller), backfill support, attachments
    Login        *LoginSpec   // Login methods (point 7)
}
```

- Type assertions are only for **dispatch**: the hub asserts `Inbox` only if the manifest declares `CapInbox`; declared but unimplemented, or implemented but undeclared, fails in `Registry.Add` (caught at startup rather than returning empty at runtime).
- Merge interfaces into seven groups: `Status` (required, with an embeddable `connector.Base` defaulting to `ok`), `Run` (merges `Runner` + `Events` + `Machines`: `Run(ctx, Host)`,
  where `Host` provides `Changed(scope)` and `MachineOnline` subscription), `Tools` (`ReadTools` + `Actions`, `Describe` can return errors, replacing `Validator`), `Inbox`, `Changes` (point 2), `Login`, `Options`.
- `capabilities` in `GET /api/v1/connectors` comes from the manifest; existing names remain unchanged, so no App changes.

Size: **small to medium**. Mechanical changes to five connectors and hub dispatch; MCP / Inbox / knowledge-base goldens must remain byte-for-byte identical.

### 2. Knowledge-base ingestion: unify as "cursor-based changes"

**Not doing this (decided 2026-11-03, V7).** Conclusions after reading the code:

- GitHub, mail, Messages and Telegram's four `Archive` implementations already use the same cursor-based changes pattern; unifying them would only rename things.
- Lark's `Items` (documents, meetings, events) returns full snapshots, not increments; forcing it into a cursor interface would still require another endpoint for document-title lookup by link.
- Lark's `Chats` (per-conversation cursors, backfill, attachment downloads) is the knowledge-base archive engine itself. An adapter would merely move code,
  with no external change, yet create the highest-risk step on the largest source.

So the three shapes stay: `Archive`, `Chats`, `Items` ("I · Knowledge-base ingestion"). The original proposal follows for the record.

The judgment then: **mostly agreed; backfill and attachments stay separate.**

Three current shapes plus scheduling: `Archive` (GitHub, mail, Messages, Telegram, already cursor-based changes), `Chats` (Lark and Moments, per-conversation cursors,
with the knowledge-base engine selecting conversations, backfilling and downloading attachments), `Items` (Lark documents, meetings, events, a full snapshot each time), `Poller` (only scheduling).

Proposal:

```go
type Changes interface {
    // The connector owns the cursor (one number, one per account, or one per conversation); the hub stores and returns it verbatim.
    Changes(ctx context.Context, cursor string, limit int) (Batch, error)
}
type Batch struct {
    Chats    []ChatBatch // New conversation messages (as today)
    Items    []kb.Item   // Documents, meetings, events (replaces Items)
    Next     string
    More     bool
    NextPoll time.Duration // Replaces Poller; 0 uses the manifest value
}
```

- The four existing `Archive` connectors: only rename and change the return structure.
- `Items`: merge into `Batch.Items`; `DocTitle` (document-title lookup by link) is not a "change", so remains an optional query (later merged into "Links" in the v1 plan).
- Lark conversations: an adapter `connector.PerChat(kb.Source)` wraps per-conversation cursors into a composite cursor, moving the engine's conversation-selection logic into the adapter.
  **Lark is the largest source and this is the highest-risk step, so do it last**, with the M0 comparison baseline (then the hub's connector_baseline_test.go, removed with the hub's Lark source in #1571) and real-data comparison required.
- **Kept separate**: reading older history (the opposite direction from "since last time") is its own optional capability, `history` (`History`, read through the hub's `connectors.history*` bus methods), not part of `Changes`; the old `kb.Backfiller` / `Engine.Backfill` path is gone; the assistant's history import drives it (`docs/assistant/knowledge.md`, "History import"). Attachments (`Download`) remain optional `Media`.
  Forcing them into `Changes` makes one cursor represent two directions and harder to understand.

Size: **medium** (almost mechanical for four connectors) **to large** (Lark). Moments moves with Lark.

### 3. Patchwork interfaces and ad hoc strings

**Agreed, except for `Kind`.**

- `InboxReplier`: merge into `Inbox.Reply(ctx, InboxReply)`, one signature. Change all five connectors; subprocess `inbox.reply` only gains a few fields, so remains compatible.
- `AgentTools`: becomes per-tool `ForAgents` in the manifest (point 1). Currently an entire connector is exposed at once, too coarse.
- `Validator`: merge into errors returned by `Describe`.
- `scope`: constants already exist, but subprocesses and nodes send strings. Make it a typed `Scope`, validate at boundaries, log and drop unknown values.
- Inbox tiers (`"action"`, `"fyi"`, `"noise"`): the connector package has no constants, so Telegram, Messages and GitHub each write their own strings. Add constants such as `TierAction`.
- **Do not make `Kind` a global enum**: these should be the connector's own terms (`review_requested`, `dm`, `ci_failed`), understood by the model through `prompts/inbox/kinds/<id>.md`.
  Declare them in the manifest instead (name, human-readable label, default tier); the hub errors on undeclared kinds, and a test checks that every declared kind is described in the prompt file.

Size: **small**.

### 4. One versioned protocol, with in-process code as an adapter

**Agreed on versioning, unification and a written spec; disagreed on making built-in connectors pass through JSON in production.**

Current state: three execution models, three conventions.

- Subprocess: no version, relies on "same build". Most fields lack JSON tags, so wire keys are Go field names (`Cursor`, `Batches`), hard for third parties to reproduce.
- node relay: five iMessage-specific methods, then hardcoded in `node/node.go` (now `serveLocalConnector` in `node/connectors.go`).
- Third party: HTTP + MCP was designed in `../plans/plan-connectors.md` ("External process") but not implemented.

Proposal:

- **Protocol v2**: JSON-RPC-style one-message-per-line (reuse `internal/rpc`, already used hub↔node and hub↔subprocess), all fields snake_case, methods mapping one-to-one to the interfaces in points 1–3:
  `initialize` (both sides report `protocol` versions; the hub supports current and previous) → program returns manifest → `status`, `changes`, `inbox.collect`, `inbox.reply`, `tools.call`, `action.describe`, `action.do`, `login.step`…;
  program calls hub: `secrets.*`, `changed`. Fixed error codes (`not_signed_in`, `rate_limited`, `unknown_method`…).
- **The same protocol on three transports** (decided: third parties use it too, not the original HTTP + MCP plan): stdin / stdout (first-party subprocesses, third-party local programs); node relay (hub sends `connector.call {id, method, params}`, node forwards verbatim to its connector,
  with iMessage's `Reader` becoming a protocol-v2 connector on the node instead of five hardcoded methods); WebSocket for resident services (third-party service runs itself and the hub connects, like `docs/integrations/daemons.md`).
- **In-process** (decided): production still calls Go interfaces directly (type checking, no copies of large message batches). Tests get a JSON round-trip adapter: the same **conformance tests**
  (`connector/conformance`) run twice for each built-in connector (direct / encode then decode), so "in-process is an implementation of the protocol" is enforced by tests, not merely written in a doc.
- **Tool descriptions**: third-party tool descriptions do not live in this repo's `prompts/`, an explicit exception to "all prompts live in prompts/" (already stated in `../plans/plan-connectors.md`).
  Can a third party attach an existing MCP server as a connector with only read tools? It can be an optional protocol capability (`tools` over MCP), not the main protocol,
  because MCP has no cursors, Inbox or login.
- **Third-party spec**: write `docs/protocol/connector-protocol.md` separately: handshake, manifest, every method's parameters/results, error codes, version rules, hard safety requirements (writes only as declared actions,
  invoked by the hub after gating; secrets only in the hub-provided `secrets`; no body text or numbers in logs; no networking in `status`), and how to run conformance tests on your program. The draft's essentials are above.

Size: **large**. Telegram (subprocess, released with personad, upgraded together, simplest) → Messages (node implementation changes, old nodes keep the five methods) → third-party spec and conformance tests.
Lark, mail and GitHub stay in the hub and only run conformance tests.

### 5. Structured Inbox attributes; hub-managed merging, muting and automatic closure

**Agreed on hub-managed merge keys, sender kinds, tags and supersession; disagreed on declarative conditions for "automatically resolved".**

Current state: all noise reduction lives in the GitHub connector (`connector/github/rules.go`): CI merges by "repository + branch" (`Thread` itself becomes `ci:<repo>@<branch>`),
bot recognition (`isBot`), muted repositories and ignored branches (GitHub's own `Options`), and closure after a successful run / branch deletion / PR merge (`followUpCI` + `Settle`).
Telegram and Messages each repeat "groups are FYI" and "bots stay out of the Inbox". Every new source repeats this, and only GitHub can be muted in the App.

Proposal: add these fields to `InboxThing`:

| Field | Meaning | What the hub handles centrally |
| --- | --- | --- |
| `Group` | Merge key (defaults to `Thread`) | Merge open items with the same `Group`; `Thread` only decides "where the reply goes" |
| `From {Name, Kind, Handles}` | Who performed the latest step; `Kind` is `person` / `bot` / `self` / `system`; `Handles` in point 6 | Rule: bots default to FYI; your own actions are not new messages |
| `Tags map[string]string` | Attributes for filtering and muting (`repo`, `branch`, `branch_role`, `chat`, `sender`) | Tag-matching mute rules (with globs), stored on the hub; the App's item menu "mute this repository / conversation / sender" works the same for every source (decided; screenshot the new UI first) |
| `Supersedes []string` | Which `Group`s this item replaces (a later successful CI run supersedes the failed group) | Close superseded open items with a stated reason |

"What counts as automatically resolved" remains observed and reported by the connector: the hub cannot know that a branch was deleted, a later run succeeded or a PR merged without calling GitHub; declarative conditions would still require the connector to check.
Unify only the reporting into two paths: push (`InboxThing.Done` + `Why`, report when observed) and pull (rename `InboxSettler.Settle` to `Check(openGroups)`,
with the hub periodically asking whether open groups are finished). Cleanup after mute/rule changes belongs to the hub and no longer needs the connector's `Settle`.

**GitHub is the first adopter**: `muted_repos` → mute rules on `repo`; `ignore_branches` → glob mute rules on `branch`; `isBot` → `From.Kind`;
CI's "repository + branch" → `Group`; later success → `Supersedes`; CI mode (off / default branch / include my PRs / all) is evaluated in the hub through `branch_role` (`default` / `mine` / `other`).
The App's GitHub settings page stays unchanged (storage moves from GitHub options to hub mute rules; old `github.inbox` config migrates on first startup).
Acceptance: read-only replay of the real data used for #584 still gives 13 Needs you items, identical before and after.

Then Telegram and Messages adopt `From.Kind` and `Tags` (delete their separate bot / group checks); Lark and mail still use the hub's own Inbox blocks,
and will attach when they adopt `InboxThing` (not done in v1; a separate task).

Size: **medium**. Hub Inbox, GitHub, Telegram, Messages; the App's mute menu is new UI, a separate PR with screenshots shown to you.

### 6. Sender identity hints

**Agreed; v2 records but does not merge. Hints store only HMAC hashes, are hidden from models, and are used only to recognize people (decided).**

Current state: knowledge-base people (`Person` in `kb/store.go`) have only one `Source` + `SourceID`; the same person has separate entries in Lark, mail, Messages and Telegram.
To keep numbers off disk, Messages already uses a phone/email hash as the person id (`PersonKey` in `connector/imessage/persona.go`).

Proposal:

- `Handle{Kind, Hash}`: `Kind` is `email` / `phone` / `github` / `telegram` / `lark`; `Hash` is an HMAC with the hub's own key after normalization (lowercase email, E.164 phone).
  The same email in mail and Messages gets the same hash, identifying the same person without writing the number to the knowledge base.
- Put it in `InboxThing.From.Handles` and `kb.SourceMessage.SenderHandles`; add `Handles []string` to `Person` (append only).
- **Hidden from models**: no hints in MCP results, Inbox classification prompts or knowledge-base compression prompts (hashes mean nothing to the model and waste context), enforced by goldens;
  raw values (phone, email) still stay off disk.
- What each source can supply: mail (address), Messages (phone / email, already its id), GitHub (login; omit email when unavailable), Telegram (user id; phone only for contacts),
  Lark (user id; email with permission).
- **Identity merging (combining entries into one person) is outside v2**: design separately once hints exist, including how to undo a bad merge and who confirms it.

Size: **small** (connector fields) **to medium** (knowledge-base writes). Small changes to all five connectors.

### 7. Login supports "open a web page to authorize"

**Agreed. Mail needs multi-account support first, so comes later.**

Current state: only Telegram uses `Login` (stepwise field entry). Gmail and Outlook use mail-specific `/api/v1/mail/oauth/{google,microsoft}/start|finish`;
GitHub reads `gh` login from a computer. The App has no generic connector login page yet (Telegram's App side is in progress).

Proposal: add two step types to `Prompt` beyond field entry:

- `open_url`: `{url, callback_scheme}`. The App opens it through system web authentication (`ASWebAuthenticationSession`), then returns the callback URL as this step's value (`callback_url`). OAuth uses this.
- `device_code`: `{url, user_code, interval}`. The App shows the code, opens the URL, then polls the same step every `interval` seconds until `done`. GitHub device-code login uses this.
- `qr` (#1351): `{url, interval}`, where `url` is content for another App to scan (WeChat QR authorization). The hub adds the QR matrix `qr: {size, rows}` to its App response (`rows` is one string of `0` / `1` per row,
  without surrounding whitespace, generated like the admin pairing QR). The App draws it (black modules on white in both dark and light, with a quiet zone), polling the same step every `interval` seconds until `done`;
  a phone cannot scan its own screen, so a "Save QR code" action appears below (share / save to Photos, then recognize it from the album in the other App). iOS / Mac, web (Settings › Connectors, #1693) and Android all have connector login pages.
- Steps the client cannot draw (unknown `kind`, `qr` without a matrix, a form with no fields) must not become an empty form with a permanently disabled "Next" (#1693): explain that the step cannot be displayed and what to do next (update and restart; for a channel, also bind in Settings › Channels), and offer "Start over".
  Web falls back to a link (copyable, still polled) when a `qr` step lacks only the matrix and `url` is http(s). iOS / Mac likewise explain that this App version cannot display the step and to update then "Start over"; QR steps also suggest scanning through web Settings › Connectors (`ConnectorPrompt.cannotDraw`).
  Android (Settings › Connectors, Settings › Channels, extension login, #4488) follows the web fallback: when a `qr` step lacks only its matrix and `url` is http(s), show a link (copy button or long-press selection) and keep polling. For other unsupported steps, explain the reason, offer "Start over" and "Cancel", and do not poll (`StepView` in `SignInSteps.kt`).

The App then has **one** generic login page (field entry, web authorization, code display), used by Telegram, Gmail, Outlook and GitHub.

`larkcli` uses the same `device_code` prompt. The manager starts the blocking `lark-cli auth login --domain all` process and returns its verification URL and user code; the App polls the same `login.step` until the process exits. A second start cancels the first one, and the manager stops it when the connector shuts down.

- **Mail**: one connector has several accounts, while today's `Login` holds one session per connector. Add an "account" layer (`login.step` carries `account`, empty to add an account; `logout` names the account).
  Keep old `/api/v1/mail/oauth/*` for old Apps.
- **GitHub**: device-code login uses the built-in GitHub CLI Client ID; users need not register an OAuth App (decided #1089, replacing user-entered IDs).
  This is `oauthClientID` in `internal/authflow/flow.go` of `cli/cli` (`178c6fc778ccc68e1d6a`, whose source comment explicitly permits committing it),
  hardcoded as `ghCLIClientID` in `server/internal/connector/github/login.go`; device-code login needs no client secret. The first step gets the code directly, and the App shows it and automatically waits for authorization.
  Older hubs stored a user-entered client ID: stop reading it and discard it on the next save; tokens obtained with it remain valid. If GitHub refuses to issue a code, report the error directly, not another ID form.
  Keep "read gh login from a computer" as an alternative.

  What the user sees:

  1. Settings › Connectors › GitHub › Login source › Device-code login › Log in; the App shows a code.
  2. Enter it at github.com/login/device. **The authorization page says "GitHub CLI"** (its OAuth App is being reused), not Persona; this is expected.
  3. GitHub lists the requested permission: only `repo` (read/write repositories, including private-repository PRs, issues, comments, reviews, CI and logs, and notifications); confirm it.
     To revoke later, find "GitHub CLI" in Settings › Applications › Authorized OAuth Apps (revoking also invalidates the same grant obtained by gh device-code login on your computers; run `gh auth login` again when needed).

Size: **medium**. Hub login API, generic App login page (new UI, screenshots shown to you), multi-account mail, GitHub device codes.

### 8. Writes are tools and must be gated; no extra gate for skills

**Connector writes still go through `connector_gate` as tools; skills get no extra gate and rely on Claude Code's own permission checks (decided 2026-11-03; V2 rejected).**

Current state (unchanged):

- Connector writes are `Actions`, gated for every AI call (`github_comment`, `github_review`, `mail_send`); manual sends in the App bypass the gate (#1190, see "Gate").
- Lark commands in the extension's skill are classified by the node's Bash hook (rules also in `connector_gate` after M5). Assistant bypass permits classified reads and ordinary writes; outbound sends as the user, deletion and unclassified writes still require confirmation. Explicit deny rules and health-space restrictions remain in force.
- User skills in `~/.persona/skills` are linked into the assistant directory; their scripts follow Claude Code's permission flow.

The former proposal generalized `larkgate.go` command classification to every skill (declare write scripts in `persona.json`, confirm on the phone at execution, #654 / #657).
The user's decision: Claude Code already authorizes skill writes; Claude judges for itself and asks when a user decision is needed. "Do not over-engineer this." So it was not implemented or merged.

The rule to make writes connector actions remains: Telegram send, reply, forward, reaction and mark-read became actions such as `telegram_send` (#988),
called through the `tg` CLI, gated with a card naming the recipient and full text; the subprocess protocol gained `actions.*` for this (`docs/protocol/connector-protocol.md`).

## IV. Decisions (2026-11-03)

1. **Overall direction and V1–V7 order**: agreed. V1 and V7 preserve external behavior, enforced by goldens and real-data comparison. V7 was later rejected (see point 2).
2. **Point 4**: built-in connectors keep direct Go calls in production; JSON round-trips happen only in tests, enforced by conformance tests.
3. **Point 4**: third-party connectors use "one JSON message per line over RPC, on stdin / stdout or WebSocket", the same protocol as subprocesses and nodes; not the original HTTP + MCP plan.
4. **Point 5**: add "mute this repository / conversation / sender" to every Inbox row's menu, for all sources. This is new UI; show screenshots first when implementing it.
5. **Point 6**: identity hints store only HMAC hashes, hidden from models, used only to recognize people.
6. **Point 7**: GitHub device-code login uses the built-in GitHub CLI Client ID, so users need not register an OAuth App; the authorization page says "GitHub CLI" (user revised the decision 2026-11-04, #1089; the original user-entered client ID decision is void), see point 7.
7. **Point 8**: initially decided "skill gate allows by default, blocks only declared write commands, applies only to the assistant"; then changed to **no skill gate**: Claude Code's own permissions govern skill writes; Claude judges and asks when needed, without over-engineering. Connector writes remain tools gated through `connector_gate`.
