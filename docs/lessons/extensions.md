# Lessons: extension settings lifecycle

- Test catalog artwork with real transparent PNGs in both appearances (#4780), not only colored mock tiles: a black GitHub mark can decode successfully and still disappear on a dark role fill. Loaded logos need a neutral light backing; a missing or failed logo keeps the earlier role-tinted glyph. PNG publication also avoids assuming every native image loader can decode SVG.
- Catalog display metadata belongs beside the signed entry, not inside its runtime manifest (#4780): an old strict manifest decoder can reject a whole package for an unfamiliar icon field. Keep signed payload bytes intact and sort the API projection, never the verified entries. `MarketView` also has a legacy mirror converted by a Go struct cast; additive fields must be added at the same position there or the old endpoint stops compiling. Preserve absent download counts separately from explicit zero.
- GitHub markets already support repository-relative installable archives through the contents API with the existing market credential (#3363). A branch-following catalog and its packages are separate reads, so publishers must retain immutable version paths; SHA256 detects changed bytes but cannot recover a deleted old archive. Direct private raw-host URLs do not receive the API-bound token. Nonofficial plain catalogs remain unsigned; repository publication does not relax official signature or owner-pin checks.
- A destructive endpoint is not a preflight. `DELETE .../{id}/-/` can return dependency blockers, but when nothing blocks it the extension is removed. Never call it to populate a confirmation dialog. If a client needs a dependency/removal-set preview and the manager does not expose one, keep the standard action visible and disabled with that specific reason; the API change is a separate task.
- `ExtensionView.kind` is a contribution category from `Manifest.Kind()`, not the installed execution runtime. Do not display UI/connectors/voice as a runtime simply because another client does. If the installed declaration's runtime is not in the response, show Not provided and document the missing read-only field.
- Attached extensions can carry installed-looking metadata. Decode the existing `attached` record before deriving market capabilities; source text or an origin alone must not turn an externally running process into a host-managed package. Keep sandbox failures and externally reported runtime versions separate from the saved Enabled preference.
- The paused automatic-upgrade switch still represents the saved preference. Do not render it off because the extension is disabled, and do not submit a dirty configuration draft when changing lifecycle preferences. Manager-bound market checks and permission previews must use the same manager as the settings page, including global automatic-upgrade reads.
- Mirror saves replace both fields, so retire the whole form on credential-generation or manager changes and bind each request to that captured context. A read waiting behind a dispatched write must check its own context again before sending; the original write may still commit. Name the selected manager in both header and query because the hub gives the header precedence over the query. Exercise shared synthetic server state through the real REST client, including late authentication and proxy responses.
- A new `NavIcon` is a hub feature first, not just an extension change. The hub checks a manifest's `ui.icon` against the icon list compiled into it (`wire.NavIcons`, generated from `schema/extension/view.schema.json`), so an extension that names an icon the deployed hub does not know fails to load whole. Put the icon in the schema and in every client, ship a hub build that carries it, and only then release the extension that names it; until then the package keeps the old icon.
